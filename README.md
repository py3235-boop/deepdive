# 발주서 자동화

고객사가 보내온 발주서를 **형식에 상관없이** 읽어 딥다이브 내부 품목코드로 변환하고,
월별 발주서 시트에 기록하는 Google Apps Script 시스템.

스프레드시트에 바인딩된 Apps Script 로만 동작한다. 웹앱·외부 서비스를 쓰지 않는다.

2026 전남·광주 청년 AI 솔버톤 출품작 (팀 딥다이브)

---

## 무엇을 해결하나

고객사 A·B·C가 매월 발주서를 보내오는데 **오는 방식과 형식이 고정돼 있지 않다.**
같은 고객사가 어떤 달은 메일 본문에 표로, 어떤 달은 PDF 첨부로, 어떤 달은 캡처 이미지로 보낸다.

지금까지는 사람이 메일을 열어 형식에 맞게 눈으로 읽고, 품명·규격·수량·중량·일자를
내부 품목코드로 손으로 옮겨 적었다. 형식이 매번 달라 읽는 방법도 매번 다르고,
품목코드 대조를 사람이 하다 보니 느리고 틀리기 쉽다.

---

## 흐름

```
[채널]  Gmail 수신 · 드라이브 폴더 투입
             ↓
[고객사 식별]  시트의 키워드 규칙표로 가중치 합산 → 최고점 고객사
               동점·0점이면 미분류 → 시트 메뉴에서 사람이 지정
             ↓
[자동 분리 저장]  고객사 첨부파일/고객사X/   (미판별은 미분류/)
             ↓
[형식 추출]  docx · xlsx · pdf(텍스트) · pdf(스캔) · png/jpg · 메일본문 HTML · csv
             ↓
[고객사별 정규화]  A / B / C 표 구조 해석
             ↓
[매핑]  변환규칙 시트 → 품목 · 품목코드 · 규격
             ↓
[검산]  합계·소계 대조 + 중량 = 수량 × 단위중량
             ↓
[기록]  해당 월 발주서 파일 → 고객사별 탭  (없으면 새로 생성)
```

## 설계에서 중요한 결정 세 가지

### 1. 외부 API 키를 쓰지 않는다

이미지·PDF 추출에 LLM 비전(Gemini 등)을 쓰지 않고 **Drive 변환·OCR 만** 쓴다.
무료 티어 일일 한도에 걸려 시연 중 멈추는 위험을 없애기 위해서다.

가능한 이유는 데이터에 있다 — **세 고객사의 매핑 키가 전부 ASCII다.**

| 고객사 | 매핑 키 | OCR 위험 |
|---|---|---|
| A | `ZWCSS-00030` (코드) | 낮음 |
| B | `7/0.26` (규격) | 낮음 |
| C | `AVSS 2.0SQ` + `37/0.260` | 낮음 |

한글(`연동집합선`)이 깨져도 매핑은 성공한다. 실측 결과 고객사B 이미지에서
**7행 전부 정확히 추출**되고 소계 검산까지 통과했다.

추출기는 `추출(입력) → {표들, 줄들, 원문}` 하나의 인터페이스로 분리했다.
특정 형식의 정확도가 부족해지면 **그 분기만 교체**하면 된다.

### 2. 발주서 자체의 숫자로 검산한다

발주서에 검산 장치가 이미 들어 있다.

| 근거 | 예 |
|---|---|
| 고객사A 납기 블록별 `합계` 행 | 수량 합 29 / 중량 합 12,356 |
| 고객사B `소계` 행 | 7행 합 69,794 = 소계 69,794 |
| 중량 = 수량 × 단위중량 | 16 × 436 = 6,976 |

합계 대조 실패는 **치명적**으로 보고 그 건 전체를 보류한다.
단위중량 대조는 참고용이다 (단위중량 자체가 시트 값이라 틀릴 수 있으므로).

이 검산 덕분에 값을 잘못 옮기면 코드가 먼저 잡아낸다. 고객사C 의 PDF 에서
숫자 세 개(조장·수량·중량) 중 어느 것이 수량인지도 **위치가 아니라 단위중량으로 판별**한다.

### 3. 규칙을 코드에 박지 않는다

| 무엇을 | 어디서 관리 |
|---|---|
| 품목코드 매핑 | `변환규칙` 시트 |
| 출력 표 레이아웃 | `고객사 발주서 양식` 시트 |
| 고객사 식별 키워드·가중치 | 관리 시트 `고객사식별` 탭 |
| 폴더·시트 ID, 메일 검색식, 트리거 주기 | 관리 시트 `설정` 탭 |

특히 **양식 시트가 곧 출력 표의 모양**이다. 왼쪽에 고객사 원본, 빈 열 하나,
오른쪽에 변환 결과가 나란히 들어가 사람이 좌우를 눈으로 대조할 수 있다.
좌표를 코드에 박지 않고 헤더 내용으로 표를 찾으므로, 시트에서 표를 옮겨도 코드를 고칠 필요가 없다.

## 산출물

```
발주서/
├── 2026-09 발주서      탭: 고객사A · 고객사B · 고객사C
└── 2026-10 발주서      10월 건이 처음 들어올 때 자동 생성
```

한 파일에 영구 누적하지 않는다. 각 탭은 이렇게 생긴다:

```
품명 | 규격 | 중량  ‖  품목 | 품목코드 | 규격 | 중량  │  출처
```

`출처` 는 클릭하면 원본으로 간다 — 메일이면 Gmail 해당 메일, 첨부·파일이면 그 파일.

### 색으로 상태를 표시한다

| 표시 | 의미 |
|---|---|
| 회색 배경 + 취소선 | 수정 발주로 **대체된** 행 |
| 연노랑 배경 | 검산 참고용 불일치 — 기록은 되지만 확인 필요 |
| 주황 셀 | 품목명 누락 |
| 기본 | 유효 |

### 수정 발주와 추가 발주를 구분한다

발주 한 줄을 식별하는 키를 정해두고, **같은 키가 다시 오면 수정**(이전 행을 대체됨으로),
**다른 키면 추가**(이전 행은 그대로 유효)로 본다. 파일 단위로 대체하면 추가 발주일 때
멀쩡한 이전 발주가 무효가 되므로 행 단위로 판단한다.

| 고객사 | 행 식별 키 |
|---|---|
| A | 발주코드 + 일자 |
| B | 규격 (일자 필드가 없는 월 단위 계획서) |
| C | 제품명 + 규격 (+ 일자) |

## 중복 처리를 막는 3중 장치

| 장치 | 어디 | 역할 |
|---|---|---|
| **식별키** | 관리 시트 `처리로그` | 실제 판단 — 유일한 진실 |
| **`_완료` 파일명** | 드라이브 파일 | 눈으로 구분 + 메일 첨부가 드라이브 스캔에 재잡히는 것 차단 |
| **읽음처리 + 라벨** | Gmail | 눈으로 구분 |

메일 경로의 식별키(`메시지ID#첨부이름`)와 드라이브 경로의 식별키(`파일ID`)가 서로 다르므로,
`_완료` 표시가 없으면 메일로 받아 저장한 첨부를 드라이브 스캔이 다시 처리한다.

## 설치

### 준비물

- Google 계정 (스프레드시트·드라이브·Gmail 접근 권한)
- [clasp](https://github.com/google/clasp) — `npm i -g @google/clasp`

### 절차

1. **드라이브 폴더 구성**

   ```
   발주서/
   ├── 고객사 첨부파일/
   │   ├── 고객사A/    (입력)
   │   ├── 고객사B/
   │   └── 고객사C/
   ├── 필요 첨부파일/
   │   ├── 변환규칙            (스프레드시트)
   │   └── 고객사 발주서 양식  (스프레드시트)
   └── 발주서/                 (출력 — 월별 파일이 생성됨)
   ```

2. **관리 시트 생성** — `발주서자동화_관리` 라는 스프레드시트를 만들고,
   **확장 프로그램 → Apps Script** 로 바인딩 스크립트를 만든다.

3. **소스 배치**

   ```bash
   git clone <이 저장소>
   cd 솔버톤
   clasp login
   clasp clone <스크립트 ID> --rootDir src
   clasp push --force
   ```

   `clasp clone` 이 `src/src/appsscript.json` 을 중첩 생성하면 한 단계 올려주고
   빈 `src/src` 를 지운다. 그러지 않으면 첫 push 가 막힌다.

4. **`00_설정.gs` 의 `기본설정` 을 자기 폴더·시트 ID 로 바꾼다.**
   또는 관리 시트 `설정` 탭에 같은 키로 넣으면 코드보다 우선한다.

5. **관리 시트를 새로고침** → `발주서 자동화` 메뉴에서 **설치 / 점검** 실행.
   권한 승인 창이 뜨면 허용한다.

6. **주기 실행** — 메뉴에서 **트리거 설치**. 기본 15분 간격.

## 사용

### 맞춤 메뉴

```
발주서 자동화
├── ▶ 전체 실행 (드라이브 + 메일)
├── ↻ 초기화 후 전체 재실행
├── 설치 / 점검
├── 트리거 설치 / 제거
├── 단계별 실행 ▸  (규칙 로드 · 추출 · 처리 · 식별 · 드라이브 수집 · 메일 수집)
├── 미분류 목록 보기
└── 산출물 초기화
```

### 미분류 건 처리

자동 판별이 실패한 파일은 `미분류` 폴더에 보관된다.
**미분류 목록 보기** 메뉴에서 목록을 확인하고 `번호 고객사` 형식으로 입력하면
(예: `1 고객사B`) 해당 고객사 폴더로 옮겨 바로 처리한다.

### 새 고객사 추가

시트 세 곳에 탭을 추가한다.

| 시트 | 추가할 것 |
|---|---|
| `변환규칙` | 고객사 탭 — `품명 / 품목 / 품목코드 / 규격` |
| `고객사 발주서 양식` | 고객사 탭 — 1행 병합 라벨, 2행 필드명 (왼쪽 ‖ 빈 열 ‖ 오른쪽) |
| 관리 시트 `고객사식별` | 판별 규칙 행 (파일명·메일제목·메일본문·문서내용·발신자) |

그리고 `00_설정.gs` 의 `고객사목록` 에 이름을 추가하고 드라이브 폴더를 만든다.
표 구조가 특이한 고객사는 `40_파서.gs` 에 전용 파서가 필요하다.

| 형식 | 추출 경로 | OCR |
|---|---|---|
| `.docx` `.doc` | Drive 변환 → 구글 문서 → 표 셀 | ❌ |
| `.xlsx` `.xls` | Drive 변환 → 구글 시트 | ❌ |
| `.pdf` | 텍스트 레이어 우선, 표가 안 나오면 OCR 재시도 | 조건부 |
| `.png` `.jpg` `.jpeg` `.gif` `.bmp` | Drive OCR (`ocrLanguage: 'ko'`) | ✅ |
| 메일 본문 | HTML `<table>` 파싱 | ❌ |
| `.csv` `.txt` | 직접 파싱 | ❌ |
| `.hwp` `.hwpx` | **미지원** — Drive 가 변환하지 못한다 | — |

## 구현 중 실제로 부딪힌 함정

기록해두지 않으면 다시 밟게 되는 것들.

**Drive OCR 은 목표 mimeType 을 지정하면 거부한다**
`Drive.Files.insert({title, mimeType: GOOGLE_DOCS}, blob, {ocr: true})` →
`OCR is not supported for files of type application/vnd.google-apps.document`.
OCR 을 켤 때는 `title` 만 주고 형식은 Drive 가 정하게 둔다.

**OCR·PDF 변환은 표 구조를 잃고 셀 하나당 한 줄로 내보낸다**
`연동집합선 / 7/0.26 / 7,980 / 연동집합선 / …` 형태. 그래서 고정 위치를 쓰지 않고
**규격 패턴이 나온 줄을 기준으로** 앞줄=품명, 뒷줄=중량으로 잡는다.

**PDF 에서 엉뚱한 줄이 숫자 묶음으로 잡힌다**
`2026 년 09 월 10 일` → `[2026, 9, 10]`, `123-45-67890` → `[123, 45, 67890]`,
품목행 자신(`AVSS 2.0SQ 37/0.260`) → `[2.0, 37, 0.260]`.
날짜·등록번호·품목행 자신을 제외하고, **품목행 뒤에 오는 가장 가까운** 숫자 줄만 쓴다.

**`GmailApp.search()` 는 보낸편지함·임시보관함까지 훑는다**
`in:inbox` 를 반드시 넣는다. 본인이 보낸 테스트 메일이 검색에 걸려 그대로 기록됐다.

**Gmail 라벨은 스레드 단위다**
검색 제외 조건으로 쓰면 같은 스레드에 답장으로 온 새 발주서가 빠진다.
라벨은 표시용으로만 쓰고 중복 판단은 메일별 식별키로 한다.

**스크립트 편집기에서 `SpreadsheetApp.getUi().alert()` 를 부르면 실행이 매달린다**
대화상자를 띄울 화면이 없어서 응답을 기다린다. 로직 함수에서는 절대 대화상자를 띄우지 않고,
팝업이 필요하면 시트 메뉴에서 부르는 래퍼(`*_메뉴`)로 분리한다.

**파일명 표기가 일관되지 않다**
`고객사B 9월 발주서.png`(공백 없음) / `고객사 A … .docx`(공백 있음).
키워드 비교 전에 양쪽 모두 **공백 제거 + 소문자화** 한다.

**구분에 쓸 수 없는 키워드가 있다**
`딥다이브` 는 세 고객사 문서에 전부 등장한다(자사명).
