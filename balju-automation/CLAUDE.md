# 발주서 자동화 — 작업 규칙

고객사 발주서를 형식에 상관없이 읽어 딥다이브 품목코드로 변환하고 월별 시트에 기록하는
Google Apps Script 시스템. **스프레드시트에 바인딩된 Apps Script 로만 동작한다.**
웹앱·외부 API·유료 서비스를 쓰지 않는다.

---

## 절대 규칙

**1. clasp 명령에는 항상 `--user company` 를 붙인다.**
`~/.clasprc.json` 에 슬롯이 여러 개라 생략하면 어디로 갈지 모른다.
회사 계정은 `company` 슬롯에 있다.

**2. `clasp logout` 을 절대 실행하지 않는다.** 사용자가 명시적으로 요청했다.

**3. clasp 는 이 폴더(`balju-automation/`)에서 실행한다.** `.clasp.json` 이 여기 있다.

```bash
cd balju-automation
clasp --user company push --force
```

**4. GitHub 에 올리기 전에 반드시 물어본다.** `git push`, `gh repo create`, 공개 범위 변경 전부.
커밋은 로컬 작업이므로 진행해도 되지만 **푸시 단계에서 멈추고 승인받는다.**
코드에 드라이브 폴더·시트 ID 가 들어 있어 공개 범위는 사용자가 판단할 몫이다.

**5. 요청받은 단계만 만들고 멈춘다.** 앞서 나가지 않는다.

**6. 자료는 사용자가 지정한 드라이브 폴더만 본다.** 로컬 파일이나 이전 프로젝트 기록을 뒤지지 않는다.

**7. 코드 파일은 직접 쓴다.** 파이썬 heredoc 같은 우회로 코드를 생성하지 않는다.
이스케이프(`\n`, `\1`)가 깨져 제어문자가 박히는 사고가 **두 번** 났다. 원인 파악에 시간이 크게 든다.

---

## 개발 흐름

Apps Script 는 로컬에서 실행할 수 없다. 흐름은 항상 이렇다:

```
1. 로컬 src/*.gs 수정
2. 문법 검사   .gs → .js 로 복사해서 node --check
3. clasp --user company push --force
4. 사용자가 스프레드시트 메뉴에서 실행 → 실행 로그를 받아 확인
```

`clasp run` 은 쓸 수 없다 (API 실행 배포가 따로 필요하다).
**첫 실행과 권한 승인은 브라우저에서만 가능하다.**

### 문법 검사

`.gs` 확장자를 `node --check` 가 거부하므로 `.js` 로 복사해서 검사한다.

```bash
for f in src/*.gs; do
  b=$(basename "$f" .gs); cp "$f" "/tmp/$b.js"; node --check "/tmp/$b.js" || echo "FAIL $f"
done
```

### 사용자에게 시트 편집을 요구하지 않는다

설정 탭에 행을 추가하는 것을 사용자가 어려워한다. **입력이 필요하면 메뉴에서 `ui.prompt` 로
받아 `설정값쓰기()` 로 저장한다.** 웹훅 설정·트리거 주기가 그렇게 되어 있다.

### 맞춤 메뉴

```
발주서 자동화
├── ▶ 전체 실행 (드라이브 + 메일)     전체_실행_메뉴
├── ↻ 초기화 후 전체 재실행           전체_재실행_메뉴
├── 설치 / 점검                       설치_메뉴
├── 트리거 설치 (주기 수집)           트리거_설치_메뉴   ← 주기를 물어본다
├── 트리거 제거                       트리거_제거_메뉴
├── 단계별 실행 ▸  규칙 로드 · 추출 · 처리 · 식별 · 드라이브 수집 · 메일 수집
├── 미분류 목록 보기                  미분류_목록_메뉴
├── 알림 설정 (Google Chat 웹훅)      알림_웹훅설정_메뉴  ← URL 을 물어본다
├── 알림 테스트                       알림_테스트_메뉴
├── 관리 시트 서식 정리               관리시트_서식_메뉴
└── 산출물 초기화                     산출물_초기화_메뉴
```

메뉴를 바꾸면 **스프레드시트를 새로고침**해야 반영된다 (`onOpen`).
코드를 바꾸면 **스크립트 편집기를 새로고침**해야 반영된다.

## 설계 원칙

### 규칙을 코드에 박지 않는다

| 무엇을 | 어디서 관리 |
|---|---|
| 품목코드 매핑 | `변환규칙` 시트 |
| 출력 표 레이아웃 | `고객사 발주서 양식` 시트 |
| 고객사 식별 키워드·가중치 | 관리 시트 `고객사식별` 탭 |
| 폴더·시트 ID, 메일 검색식, 트리거 주기, 챗 웹훅 | 관리 시트 `설정` 탭 (코드의 `기본설정` 보다 우선) |

**`고객사 발주서 양식` 시트가 곧 출력 표의 모양이다.** 왼쪽=고객사 원본, 빈 열 하나,
오른쪽=변환 결과. 좌표를 박지 않고 **헤더 내용으로 표를 찾으므로** 시트에서 표를 옮겨도
코드를 고칠 필요가 없다.

### 추출기는 교체 가능한 인터페이스

`추출(입력) → {표들, 표배경들, 줄들, 원문, 메타}` 하나로 통일했다.
특정 형식의 정확도가 부족해지면 **그 분기(`_추출_*`) 하나만 갈아끼운다.** 상위 계층은 손대지 않는다.

### 파서는 고정 위치를 쓰지 않는다

OCR·PDF 변환은 표 구조를 잃고 **셀 하나당 한 줄**로 내보낸다. 그래서
**규격 패턴(`숫자/숫자`)이 나온 줄을 기준으로** 앞줄=품명, 뒷줄=중량 을 잡는다.
고객사C 는 숫자 세 개 중 어느 것이 수량인지 **위치가 아니라 `중량 = 수량 × 단위중량`** 으로 가린다.

### 검산은 발주서 자체의 숫자로 한다

합계·소계 행 대조가 **치명적**(실패 시 그 건 전체 보류), 단위중량 대조는 **참고용**
(단위중량 자체가 시트 값이라 틀릴 수 있다).

### 추가 발주와 변경 발주

같은 품목·같은 납기일로 다시 오면 데이터만으로는 구분할 수 없다. 사람이 쓴 말로 가린다.

| 제목·본문·파일명 | 판정 | 동작 |
|---|---|---|
| `추가` | 추가 | 기존 행 유지 + 그 납기일 블록에 끼워넣고 **합계 재계산** |
| `수정` `변경` `정정` `재발주` | 변경 | 같은 키 행을 취소선 처리 |
| **없음** | **변경** (기본) | 같은 키 행을 취소선 처리 |

**변경을 기본으로 둔 이유:** 같은 발주서를 실수로 두 번 보내는 일이 흔한데, 추가가 기본이면
발주량이 조용히 두 배가 된다. 취소선은 눈에 보이지만 두 배 수량은 안 보인다.

추가 발주일 때 **들어온 문서의 합계는 버린다.** 그건 그 문서만의 합계라 시트에 쓰면 틀린 값이 된다.
시트의 살아 있는 행(취소선 아닌 행)을 전부 더해 블록 합계를 갱신한다.

## 산출물 규칙

```
발주서/
├── 2026-09 발주서   탭: 고객사A · 고객사A 원본 · 고객사B · 고객사B 원본 · 고객사C · 고객사C 원본
└── 2026-10 발주서
```

**고객사 탭** — 양식 열 + 출처 링크 한 열. 추적 정보는 관리 시트 `처리로그` 에 있으므로 넣지 않는다.

**원본 탭** — 표가 있으면 그대로(고객사A 메일 표: 업체코드·출고처까지 전부, HTML 배경색 포함),
표가 없으면(B 이미지 OCR, C PDF) 양식 왼쪽 블록 형태로 재구성. **제목 줄·출처 줄을 두지 않는다.**

### 색 규칙

| 표시 | 의미 |
|---|---|
| 흰색 | 유효 |
| **연보라** `#ede7f6` | 추가 발주로 나중에 들어온 행 |
| 회색 + 취소선 | 변경 발주로 대체된 행 |
| 회색 굵게 | 합계 행 |
| 연노랑 | 검산 참고용 불일치 (확인 필요) |
| 주황 셀 | 품목명 누락 |
| 헤더 파랑 / 초록 | 왼쪽=고객사 원본 / 오른쪽=딥다이브 변환 |

**배경은 좌우 블록과 출처 열에만 칠한다.** 전체 폭을 칠하면 사이 빈 열까지 색이 들어가
좌우 구분이 흐려진다 (`_블록배경` 이 이 일을 한다).

정렬은 **전부 가운데**, 수치 열에는 천단위 콤마(`#,##0`).

## 함정 — 다시 밟지 않도록

### Apps Script / Google API

**로직 함수에서 대화상자를 띄우면 실행이 매달린다.**
스크립트 편집기에서 실행하면 `SpreadsheetApp.getUi().alert()` 를 보여줄 화면이 없어
응답을 기다리며 멈춘다. 팝업은 시트 메뉴에서 부르는 래퍼(`*_메뉴`)로만 분리한다.

**`getFilesByName()` 은 휴지통에 있는 파일도 돌려준다.**
`isTrashed()` 로 걸러내지 않으면 `산출물_초기화` 로 버린 파일을 다시 찾아 거기에 기록하고,
알림 링크가 휴지통 파일을 가리킨다. **실제로 그렇게 됐다.** ID 로 여는 경로도 마찬가지다.

**Drive OCR 은 목표 mimeType 을 지정하면 거부한다.**
`Drive.Files.insert({title, mimeType: GOOGLE_DOCS}, blob, {ocr: true})` →
`OCR is not supported for files of type application/vnd.google-apps.document`.
OCR 을 켤 때는 `title` 만 주고 형식은 Drive 가 정하게 둔다.

**`GmailApp.search()` 는 보낸편지함·임시보관함까지 훑는다.**
`in:inbox` 를 반드시 넣는다. 본인이 보낸 테스트 메일이 걸려 그대로 기록된 적이 있다.

**Gmail 라벨은 스레드 단위다.**
검색 제외 조건으로 쓰면 같은 스레드에 답장으로 온 추가 발주가 통째로 빠진다.
라벨은 표시용으로만 쓰고 중복 판단은 메일별 식별키로 한다.

**`SpreadsheetApp.create()` 는 내 드라이브 루트에 만든다.**
만든 뒤 목표 폴더로 `addFile` 하고 루트에서 `removeFile` 해야 한다.

**시트 인덱스 기준이 API 마다 다르다.**
`Sheet.getIndex()` 1부터 / `insertSheet(이름, 위치)` 0부터 / `moveActiveSheet(위치)` 1부터.
섞어 계산하다 탭 순서가 어긋났다. **위치 지정 없이 만들고 나중에 `탭순서정리()` 로 정렬**한다.

**`getRange(행, 열, 행수, 0)` 은 거부된다.**
원본 탭처럼 오른쪽 블록이 없는 레이아웃도 있으니 폭 0 을 먼저 걸러낸다.

**`clasp push` 실패 두 가지**
`Precondition check failed` → 일시적. 그냥 재시도한다.
`invalid_grant / invalid_rapt` → Google 이 주기적으로 요구하는 재인증.
사용자에게 `! clasp login --user company` 를 부탁한다.

### 데이터

**구분에 쓸 수 없는 키워드가 있다.**
`딥다이브` 는 세 고객사 문서에 전부 등장한다(자사명).
`AVSS 2.0SQ` `37/0.260` 은 고객사A 와 C 양쪽에 등장한다.

**파일명 표기가 일관되지 않다.**
`고객사B 9월 발주서.png`(공백 없음) / `고객사 A … .docx`(공백 있음).
키워드 비교 전에 양쪽 모두 **공백 제거 + 소문자화**(`키정규화`) 한다.

**PDF 에서 엉뚱한 줄이 숫자 묶음으로 잡힌다.**
`2026 년 09 월 10 일` → `[2026, 9, 10]`, `123-45-67890` → `[123, 45, 67890]`,
품목행 자신(`AVSS 2.0SQ 37/0.260`) → `[2.0, 37, 0.260]`.
날짜·등록번호·품목행 자신을 제외하고 **품목행 뒤에 오는 가장 가까운** 숫자 줄만 쓴다.

**고객사C 는 중량이 `금액` 열이 아니라 `비고` 열에 있다.** 열 이름만 믿으면 안 된다.

**고객사A 의 발주코드는 `-P` 접미사가 붙는다.** 변환규칙의 키는 `ZWCSS-00030` 이므로
`발주코드에서코드()` 로 떼고 찾는다.

**합계 행의 키는 따로 만든다.**
고객사B 는 행 키가 `규격` 하나뿐인데 합계 행은 규격이 비어서 키가 빈 문자열이 되고,
대체 판정에서 걸러져 **변경 발주 때마다 합계 행이 쌓인다.** `_합계키(일자)` 를 쓴다.

### 도구

**정규식·이스케이프가 든 코드는 파일을 직접 쓴다.**
파이썬 문자열에서 `\1` 이 8진수 이스케이프(chr(1))로 해석돼 정규식에 제어문자가 박히고,
메일 본문 표를 못 찾는 버그가 났다. `\n` 이 실제 줄바꿈이 되어 문법 오류가 난 적도 있다.
**두 번 다 원인 파악에 시간이 크게 들었다.**

## 검증

산출물은 API 로 내용만 읽을 수 있고 **색·테두리·탭 순서는 사용자가 눈으로 봐야 한다.**
서식을 바꿨으면 확인을 요청한다.

### 기대값 (샘플 데이터 기준)

## 하지 않는 것

- LLM 비전 / 외부 API 키 (한도·정책 리스크. 추출기 분기 교체는 언제든 가능)
- 웹앱 (사용자가 범위에서 제외했다. 시트 메뉴와 트리거로 충분)
- 한글 파일(`.hwp` / `.hwpx`) 지원 — Drive 가 변환하지 못한다
- GitHub Actions 자동 배포 (자격증명 유출 위험)
- 발주량을 새로 산출하는 로직 — 범위는 **받은 발주서 읽기→변환→기록**까지다

## 코드 스타일

- **함수·변수 이름은 한글**로 쓴다. 시트 컬럼명(`품목코드`·`변환규칙`)과 일치해 대조하기 쉽다.
  파일명만 영문이다 (git 이 한글 파일명을 옥탈 이스케이프로 출력해 읽기 어려웠다).
- 내부 전용 함수는 `_` 로 시작한다.
- 실패는 예외를 던지지 않고 **결과 객체에 사유를 담아 올려보낸다.** 한 건이 실패해도 나머지를 처리한다.
  알림·서식·탭 정리처럼 부수적인 일은 `try/catch` 로 감싸 **본류를 막지 않게** 한다.
- 주석은 **왜 그렇게 했는지**를 적는다. 무엇을 하는지는 코드가 말한다.
