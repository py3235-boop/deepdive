## 확정된 설계 결정

### 외부 API 키를 쓰지 않는다

이미지·PDF 추출에 LLM 비전(Gemini 등)을 쓰지 않고 **Drive 변환·OCR 만** 쓴다.

**이유:** AI Studio 무료 티어 일일 요청 한도가 낮아 개발 중 테스트로 소진되고 시연 중 멈출 위험이 있다.

**가능한 근거:** 세 고객사의 매핑 키가 전부 ASCII 다 —
A `ZWCSS-00030`(코드) / B `7/0.26`(규격) / C `AVSS 2.0SQ`+`37/0.260`.
한글(`연동집합선`)이 깨져도 매핑은 성공한다.

**실측:** 고객사B 이미지에서 **7행 전부 정확히** 추출되고 소계 검산(69,794)까지 통과했다.
한글도 깨지지 않았다.

### 출력은 월별 파일 · 고객사별 탭

한 파일에 영구 누적하지 않는다. **행마다 월을 판정**해서(일자 필드 → 파일명·제목의 `N월` →
메일 수신월) 한 파일에 여러 달이 섞이면 각 월 파일로 나눠 넣는다.

탭 순서는 `탭순서정리()` 가 고정한다: `고객사A · 고객사A 원본 · 고객사B · …`

### 합계 행을 산출물에 넣는다

| 고객사 | 합계 출처 |
|---|---|
| A | 원본의 `합계` 행 (납기 블록마다) |
| B | 원본의 `소 계` 행 |
| C | **원본에 없어 계산해서 붙인다** — 파생값이라 검산에는 쓰지 않는다 |

합계 행은 **검산 합산에서 제외**한다 (대조 기준값이지 더할 대상이 아니다).

### 추가 발주와 변경 발주를 사람의 말로 가린다

같은 품목·같은 납기일로 다시 오면 데이터만으로는 구분할 수 없다.
제목·본문·파일명에 `추가` 가 있으면 추가, `수정`/`변경`/`정정`/`재발주` 면 변경,
**아무것도 없으면 변경(기본)**.

**변경을 기본으로 둔 이유:** 같은 발주서를 실수로 두 번 보내는 일이 흔한데, 추가가 기본이면
발주량이 조용히 두 배가 된다. 취소선은 눈에 보이지만 두 배 수량은 안 보인다.

**추가 발주 처리:** 기존 행을 대체하지 않고 **그 납기일 블록의 합계 행 바로 앞에 끼워 넣는다.**
들어온 문서의 합계는 버리고(그 문서만의 합계라서), 시트의 살아 있는 행을 전부 더해 블록 합계를 갱신한다.
새로 넣은 행은 **연보라 배경**으로 표시한다.

**행 식별 키**

| 고객사 | 키 |
|---|---|
| A | 발주코드 + 일자 |
| B | 규격 (일자 필드가 없는 월 단위 계획서) |
| C | 제품명 + 규격 (+ 일자) |
| 합계 행 | `__합계__` + 일자 (전용 키 — 없으면 B 에서 합계 행이 쌓인다) |

### 발주서만 저장한다

메일 첨부 중 **제목·본문·파일명에 `발주` 가 있는 것만** 고객사 폴더에 저장한다.
지원하지 않는 형식(`.hwp`·`.zip`)은 저장하지 않고 기록만 남긴다.
고객사가 발주서와 함께 보내는 회사소개서·견적서로 폴더가 지저분해지는 것을 막는다.

### 중복 처리를 막는 3중 장치

| 장치 | 어디 | 역할 |
|---|---|---|
| **식별키** | 관리 시트 `처리로그` | 실제 판단 — 유일한 진실 |
| **`_완료` 파일명** | 드라이브 파일 | 눈으로 구분 + **메일 첨부가 드라이브 스캔에 재잡히는 것 차단** |
| **읽음처리 + 라벨** | Gmail | 눈으로 구분 |

메일 경로의 식별키(`메시지ID#첨부이름`)와 드라이브 경로의 식별키(`파일ID`)가 서로 다르므로,
`_완료` 표시가 없으면 메일로 받아 저장한 첨부를 드라이브 스캔이 다시 처리한다.

### 메일 검색은 받은편지함 · 안읽음만

```
in:inbox is:unread ("고객사A" OR "고객사B" OR "고객사C") newer_than:60d
```

읽음처리와 짝을 이뤄 대기열이 된다 — **안읽음=처리 대기, 읽음=처리 완료.**
담당자가 먼저 열어보면 자동 수집에서 빠지지만, 안읽음으로 되돌리면 다시 잡힌다.

**Gmail 라벨을 검색 제외 조건으로 쓰지 않는다.** 라벨은 스레드 단위라, 같은 스레드에
답장으로 온 추가 발주가 통째로 빠진다. 라벨은 표시용일 뿐이다.

### 트리거는 드라이브와 메일을 모두 훑는다

`자동수집()` 이 `드라이브수집()` + `메일수집()` 을 차례로 부른다.
메일만 돌리면 고객사 폴더에 파일을 직접 넣었을 때 아무 일도 일어나지 않는다.
한쪽이 실패해도 다른 쪽은 진행하고, **수집 자체가 실패하면 🚨 로 Chat 알림을 보낸다**
(조용히 멈춰 있는 게 제일 위험하다).

### Google Chat 알림

기록이 끝나는 `기록()` 한 곳에서 보낸다 — 드라이브·메일첨부·메일본문·수동지정 네 경로를 다 덮는다.

| 상황 | 문구 |
|---|---|
| 첫 발주 | `🔔 [고객사A] 발주서 도착!` / `9월 통합 문서에 추가되었습니다.` |
| 추가 발주 | `🔔 [고객사A] 추가 발주서 도착!` |
| 변경 발주 | `🔔 [고객사A] 수정 발주서 도착!` / `(이전 N행은 취소선 처리)` |
| 문제 있음 | `⚠️ [고객사A] 발주서 확인 필요` + 사유 + 관리 시트 링크 |

**알림 실패가 발주서 처리를 막지 않는다.** 예외를 삼키고 로그만 남긴다.

### 산출물에는 양식 열 + 출처 링크만

채널·처리일시·검산은 관리 시트 `처리로그` 에 남으므로 산출물에 두면 중복이다.
`출처` 는 형식만 짧게(`메일`·`PDF`·`이미지`) 쓰고 클릭하면 원본으로 간다.

**배경은 좌우 블록과 출처 열에만 칠한다.** 전체 폭을 칠하면 사이 빈 열까지 색이 들어가
좌우 구분이 흐려진다.

### 원본 탭

`고객사X 원본` 탭에 추출 내용을 남긴다. **제목 줄·출처 줄 없이 표만.**
- **표가 있으면 그대로** — 고객사A 는 메일 본문 표가 그대로 오므로 양식이 버린
  `업체코드`·`업체명`·`코드`·`출고코드`·`출고처` 까지 전부 남고, HTML 배경색도 옮긴다
- **표가 없으면**(B 이미지 OCR, C PDF) **양식 왼쪽 블록 형태**로 재구성한다

출처 링크가 진짜 원본을 보여주지만, 원본 탭은 **추출·OCR 이 뭘 어떻게 읽었는지** 확인하는 용도다.

## 제출 전 결정할 것

시트를 `링크가 있는 모든 사용자` 로 열면 **드라이브 ID 가 곧 접근 열쇠**가 된다.
GitHub 공개와 겹치면 코드에서 ID 를 읽어 실제 시트를 열 수 있다.

| 방법 | 내용 |
|---|---|
| **A. 심사용 사본** | 업무용 시트는 제한 유지, 사본만 링크 공개. 가장 안전 |
| **B. GitHub private 유지** | 시트만 링크 공개, 코드는 심사위원 초대로 |
