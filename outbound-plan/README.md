# 출고계획 자동화

세 고객사(고객사A/고객사B/고객사C)의 월별 발주 내역을 읽어, 업체별 배송 규칙(요일·트럭 상한)과
실제 생산capa를 반영한 **출고계획**을 자동으로 세우는 Google Apps Script 시스템.

스프레드시트에 바인딩된 Apps Script로만 동작한다. 외부 API·유료 서비스를 쓰지 않는다.

2026 전남·광주 청년 AI 솔버톤 출품작 (팀 딥다이브)

---

## 무엇을 해결하나

발주량을 트럭에 실어 보내는 계획은 단순히 "발주량 ÷ 일수"로 나눌 수 없다. 하루에 트럭 1대
(5,000kg)만 나갈 수 있고, 공휴일에는 배송이 안 되며, 무엇보다 **주문받은 만큼이 실제로 생산돼
있어야** 출고할 수 있다. 지금까지는 이 세 조건(트럭 상한·공휴일·생산capa)을 사람이 감으로
맞춰가며 계획을 짰다.

이 프로젝트는 발주서 → 출고계획 사이의 이 배분 작업을 자동화한다. 전체 파이프라인에서는
`balju-automation`(발주서 판독)이 만든 발주서를 읽어, `production-planning`(생산계획)이 읽어갈
**"N월 출고계획(통합)"** 시트를 만드는 중간 단계를 맡는다.

---

## 흐름

```
[입력]  발주서 파일 (고객사 A/B/C 탭, 1행 "딥다이브" 마커로 표 시작 위치 판별)
             ↓
[업체 판별]  시트명 "고객사 X" 패턴 → "고객사X"로 매핑
             ↓
[업체 타입별 배분]  전 업체 트럭버킷 방식(요일 고정 기준일 + 트럭 1대 상한 + 라운드로빈)
             ↓
[공휴일 회피]  기준일이 휴일과 겹치면 전사 기준 가장 한가한 근무일로 시프트
             ↓
[생산capa 검증]  기준정보.xlsx 기반 호기별 미니 생산스케줄링 → 기초재고가 적정재고를
                넘어서는 만큼만 배정, 부족하면 다음 배정일로 미룸
             ↓
[소량 자투리 병합]  트럭 절반(2,500kg) 미만 배정은 안전할 때만 다음 배정일로 합침
             ↓
[출력]  출고계획 시트(품목별/회사별 보기) + 발주스냅샷/지문 + 실행이력 + 챗 알림
             ↓
[2단계: 실적 반영]  74340 실적 파일 → 과거 날짜는 실적으로 덮어쓰고, 잔여물량만 "오늘 이후"로 재배분
```

## 설계에서 중요한 결정

### 1. 반올림 대신 "단위중량 1개씩" 라운드로빈

트럭 상한을 지키려고 "연속값으로 나눈 뒤 단위중량 배수로 반올림"하는 방식을 쓰면, 반올림 오차가
다른 날짜로 넘어가면서 하루 상한을 다시 넘기는 문제가 반복된다. 그래서 처음부터 끝까지 **한 번에
단위중량(보빈) 1개씩만** 배정하는 라운드로빈으로 바꿨다 — 반올림이라는 단계 자체가 없으므로
애초에 상한을 넘는 값이 나올 수 없다.

### 2. 생산capa 부족은 "경고"가 아니라 "배정 자체를 미룸"

기초재고가 적정재고(안전재고)에 못 미치는 품목은 월초엔 출고 가능량이 0에 가깝다. 이걸 무시하고
원래 날짜에 배정해버리면 실제로는 안전재고 밑으로 출고하는 계획이 된다. 그래서 그 주에 생산capa가
전혀 안 열리면 배정 자체를 건너뛰고, 생산이 쌓인 다음 배정일로 넘긴다. 월말까지 가도 정말 못
채우는 경우에만 최후수단으로 capa를 넘겨 배정하고 경고를 남긴다.

### 3. 비밀값은 스크립트 속성으로만

드라이브 폴더 ID, 구글챗 웹훅 URL 같은 값은 코드에 직접 적지 않고 전부
`PropertiesService.getScriptProperties()`로만 읽는다. 이 저장소에 커밋되는 코드에는 실제 값이
어디에도 남지 않는다.

### 4. xlsx 참고파일은 재변환 대신 캐시

기준정보/공휴일/제품중량/발주서처럼 xlsx로 올라오는 파일은 구글시트로 변환해야 읽을 수 있는데,
이 변환 자체가 매번 몇 초~십수 초씩 걸린다. 원본이 실제로 안 바뀌었으면(파일 ID·수정시각 동일)
재변환 없이 지난번 변환 사본을 스크립트 속성에 캐시해뒀다가 그대로 재사용한다(`ReadOrders.gs`,
`ReferenceFiles.gs`). 원본이 바뀌었을 때만 다시 변환한다.

### 5. 시트 쓰기는 배열로 모았다가 한 번에

품목 행마다 Range API를 따로 호출하면(특히 SUM 수식 설정) 품목 수가 많을 때 실행 시간이 크게
늘어난다. `WritePlan.gs`는 값·서식을 전부 배열로 모아뒀다가 `setValues`/`setNumberFormats`/
`setFontWeights`/`setFontColors`/`setHorizontalAlignments`를 딱 한 번씩만 호출한다. 합계·소계
열도 수식 대신 이미 메모리에 있는 값을 직접 계산해서 채운다.

### 6. 동시 실행은 LockService로 직렬화

자동 감지 트리거가 도는 도중에 수동 실행이 겹치거나 트리거끼리 겹치면, 스냅샷/지문 탭을 만드는
"있으면 쓰고 없으면 만들어라" 로직이 동시에 같은 탭을 만들려다 실패할 수 있다. `generatePlan()`과
`applyActualShipment()` 둘 다 `LockService.getScriptLock()`으로 감싸서, 겹쳐 실행되면 뒤에 들어온
쪽은 최대 30초까지 기다렸다가 그래도 안 풀리면 에러 없이 건너뛴다.

## 연동 참고

`production-planning`이 우리 출고계획을 파일명 패턴으로 찾아 읽어가므로, 그쪽이 기대하는 형식에
맞춰뒀다:

- **파일명**: `generatePlan()`이 실행될 때마다 스프레드시트 파일 이름 자체를 `N월_출고계획(통합)`으로
  맞춘다(`WritePlan.gs`) — `production-planning`이 찾는 `/^\d{1,2}월_출고계획\(통합\)/` 패턴과 일치.
- **업체 표기**: 내부적으로 전부 `고객사A` / `고객사B` / `고객사C` 형태를 쓴다(`VENDOR_TYPE_MAP`,
  발주서 탭 인식, 실적 파일의 납품처 인식 전부 동일).
- **헤더**: `품목코드 · 규격 · 구분(고객사) · 발주량 · 합계 · 날짜열…` — `발주량`(원래 발주 총량)과
  `합계`(실제 배정된 합, 정상적으로는 같은 값)를 둘 다 넣었다. `규격`은 우리 쪽에서만 쓰는 참고
  컬럼이라 이름으로 찾아 읽는 쪽에는 영향이 없다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `Config.gs` | 설정값(`CONFIG`) — 폴더 ID·웹훅 URL은 스크립트 속성에서 읽음. 업체→배송타입 매핑(`VENDOR_TYPE_MAP`) |
| `Main.gs` | 진입점 `generatePlan()` — 발주지문 비교로 재계산 스킵, 업체 순서대로 배분 호출, 시트 기록까지 총괄 |
| `ReadOrders.gs` | 발주서 파일(또는 테스트 모드 시 이 시트 자체)에서 "고객사 X" 탭을 읽어 발주 객체 배열로 변환 |
| `Allocate.gs` | 요일 균등분배 로직(트럭버킷이 아닌 타입용) |
| `TruckBucket.gs` | 핵심 배분 엔진 — 트럭버킷 라운드로빈, 생산capa 필터, 공휴일 시프트, 소량 자투리 병합 |
| `ProductionCapa.gs` | 기준정보.xlsx의 기초재고/적정재고 + `MachineSchedule.gs` 결과를 누적한 날짜별 생산capa 곡선 |
| `MachineSchedule.gs` | 호기(설비)별 미니 생산스케줄링 시뮬레이션 — 우선순위/안되는품목/설비교체 반영 |
| `OrderSnapshot.gs` | 발주스냅샷(변경 품목 강조용) + 발주지문(MD5, 재계산 스킵 판단용) 저장/로드 |
| `ActualShipment.gs` | 실적 반영(2단계) — 74340 실적 파일로 과거 날짜를 덮어쓰고 잔여물량 재배분 |
| `WritePlan.gs` | 출고계획 시트 렌더링(품목별/회사별 보기, 신규·변경 품목 색 강조), 보기 전환·초기화 |
| `ReferenceFiles.gs` | 참고파일(공휴일/기준정보/제품중량) 탐색·xlsx 변환(캐시) 헬퍼, 공휴일 Set, 단위중량 조회 |
| `AutoTrigger.gs` | 발주서 파일 변경 자동 감지(데모용) — 1분 시간 트리거 안에서 5초 간격으로 폴링 |
| `Util.gs` | 날짜 유틸, 실행이력 기록, 구글챗 웹훅 알림 |
| `더미데이터생성.gs` | 테스트용 발주서 파일 생성(실제 품목코드/규격 사용) |

## 설치

### 준비물

- Google 계정 (스프레드시트·드라이브 접근 권한)
- [clasp](https://github.com/google/clasp) — `npm i -g @google/clasp`
- (xlsx 참고파일을 그대로 쓸 경우) Apps Script 편집기 좌측 "서비스" → `Drive API`(고급 서비스) 추가

### 절차

1. 출고계획 결과를 쓸 스프레드시트를 만들고 확장 프로그램 → Apps Script 로 바인딩
2. 이 폴더(`code/`)의 `.gs` 파일 전체를 편집기에 반영 (`clasp push` 또는 직접 붙여넣기)
3. 편집기 좌측 톱니바퀴 → 스크립트 속성에 등록:

   | 속성 | 값 | 비어있으면 |
   |---|---|---|
   | `ORDER_FOLDER_ID` | 'YYYY-MM 발주서' 파일이 있는 드라이브 폴더 ID | 이 시트 자체의 "고객사 A/B/C" 탭을 발주서로 간주(테스트 모드) |
   | `REFERENCE_FOLDER_ID` | 공휴일/기준정보/제품중량 파일이 있는 폴더 ID | 공휴일 회피·생산capa 검증을 스킵 |
   | `CHAT_WEBHOOK_URL` | 구글챗 스페이스 웹훅 URL(스페이스 링크 아님, "앱 및 통합→웹훅 추가"로 발급) | 알림을 조용히 건너뜀 |

4. 시트 새로고침 → "출고계획 실행" 메뉴 확인

## 사용

```
출고계획 실행
├── ① 계획 생성                 generatePlan() — 발주서 읽어서 출고계획 작성
├── ② 실적 반영                 applyActualShipment() — 74340 실적 반영, 잔여물량 재배분
├── ③ 회사별로 보기             재계산 없이 업체별 배너로 다시 그림
├── ④ 품목별로 보기 (기본)      재계산 없이 품목순으로 다시 그림
├── ⑤ 초기화 (데모용)           빈 "기본 시트" 탭만 남기고 실제 데이터 탭은 지움
├── 발주서 자동 감지 시작(데모용) 1분 트리거(내부 5초 폴링)로 발주서 변경 시 자동 재실행
├── 발주서 자동 감지 중지
└── ⑥ 테스트 발주서 생성(디버깅용) ORDER_FOLDER_ID 자동 등록 + 테스트 발주서 파일 생성
```

발주 내역이 지난 실행과 완전히 같으면(발주지문 비교) `generatePlan()`은 재계산을 건너뛴다.
강제로 다시 만들려면 `forceRegeneratePlan()`을 편집기에서 직접 실행한다.

실제 데이터가 담긴 탭은 "N월 출고계획"(발주서 파일명 기준 연/월)이라는 별도 탭에 쓰고, 달마다
따로 남는다 — 오늘 날짜 기준 이번 달 탭만 항상 1번째로 온다(다른 파트가 첫 번째 탭만 읽으므로).

## 알려진 한계

**설비가 수요보다 부족하면 생산capa가 들쭉날쭉해진다** — 기준정보.xlsx의 "집합기" 설비가 10대인데
이번 달 대상 품목들이 원하는 최대가동수 합이 그보다 많으면, 우선순위에서 밀리는 품목은 어떤 주는
크게, 어떤 주는 조금만 생산capa를 받는다. 그 결과 트럭의 일부만 채우는 배정일이 가끔 생길 수
있다 — 스케줄링 로직의 버그가 아니라 설비 부족이라는 실제 제약의 반영이다.

**기초재고 탭의 반복 행 해석이 불확실하다** — 같은 품목코드가 여러 행(422, 422, 419, 419, 417…)으로
반복되는데 날짜 컬럼이 없어 정확한 의미(이력인지 단순 중복인지)를 알 수 없다. 지금은 첫 번째
값만 기초재고로 쓴다.

**자투리 마무리는 반올림을 쓴다** — 월말에 정말 더 미룰 데가 없을 때, 남은 물량을 단위중량으로
반올림해서 마지막 배정일에 넣는다. 이 과정에서 최대 단위중량 1개만큼 실제 발주량과 오차가 생길
수 있다.
