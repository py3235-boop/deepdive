# 집합공정 생산계획 자동화 (AI 솔버톤 — 팀 딥다이브)

## 응답 언어

- 모든 응답은 반드시 한국어로 작성한다.

## 참조 범위 (문서·코드)

- 이 프로젝트 폴더(`생산계획생성/`) 안의 파일만 읽고 참조한다. 폴더 밖의 문서·코드·다른 프로젝트 폴더(추가 작업 디렉터리 포함)는 읽어오지 않는다.
- CLAUDE.md가 언급하는 외부 문서(`06_설비별_계획_현장배포_설계.md` 등)가 이 폴더에 없으면 찾지 않고, CLAUDE.md에 적힌 내용만으로 진행한다.
- 진행 순서는 #1 → #8 단계 순서를 따른다. 사용자가 다음 단계로 넘어가자고 하면 그 단계만 수행한다.
- **브라우저 원격 조작 금지**: Chrome 자동화로 스프레드시트를 편집하거나 GAS 함수를 실행하지 않는다. 실행은 사용자가 직접 하고, 나는 실행 로그와 Drive 읽기로 결과를 대조한다 (사용자 지시, 2026-09-03).
- **한 단계씩**: 한 단계의 검증이 끝나고 사용자가 확인하기 전에는 다음 단계 코드를 작성·배포하지 않는다. 사용자가 진행 과정을 따라올 수 있어야 한다 (사용자 지시, 2026-09-03 — "2번까지만 하고 멈춰서 한 단계 한 단계 밟아갈 거야").
- 용어: 각 단계는 **"#N 단계명"**(예: `#2 출고계획 변환`)으로 부른다. 코드 주석·작업일지·커밋 메시지·스킬 문서 등 코드와 문서 본문에서 단계를 다른 이름으로 부르지 않는다 (사용자 지시, 2026-09-03).

## 프로젝트 목적

고객사 출고계획 스프레드시트 `X월_출고계획(통합)`(판독 파트가 프로젝트 루트 아래 어딘가에 둠) → **출하계획 스프레드시트로 변환(②)** → 집합공정 생산계획 자동 수립(③) → 담당자 알림(④). 이 프로젝트는 ②③④를 만든다. (발주 문서 판독 ①은 **판독 파트 담당** — 판독 파트가 검수 화면에서 확정한 발주도 같은 출하계획 스프레드시트에 행으로 들어온다.)
**출하계획·출고계획·생산실적·출하실적은 기준정보와 별개 파일이다. 기준정보에는 이 넷이 들어가지 않는다** (실적은 매일 새로 올라오는 파일이라 기준정보 탭에 두지 않는다). 출하계획 파일은 사람이 만들지 않는다 — `convertOrderToPlan()`이 첫 변환 때 기준정보와 같은 폴더에 자동 생성하고 이후 upsert한다. 출고계획 파일은 **폴더명·위치가 아니라 파일명 패턴으로 찾는다** (판독 파트의 폴더명은 정해져 있지 않음).
입력은 **기준정보 스프레드시트 1개(탭 = 데이터 종류, 우리 파트 관리) + 출하계획 스프레드시트 1개(변환 산출물 = 판독 파트 인터페이스)**, 출력은 **결과 스프레드시트 1개(고정 ID, 탭 내용만 덮어씀)**, 알림은 기본 Google Chat 웹훅(CFG.NOTIFY.channel로 텔레그램 봇·MailApp 교체 가능 — 웹훅 발급 실패 시 폴백). 파일을 매번 새로 만들지 않는다.
결과 파일은 기존 운영의 **월 통합 생산계획 파일** 역할(항상 최신 계획)이고, 실행마다 일별생산계획/에 남는 사본이 기존의 **일일생산계획 파일** 역할이다. 과거 계획 열람은 기준정보 파일의 [▶ 생산계획] 메뉴 → 결과 파일 [이력] 탭의 사본URL로 한다.

## 범위 (고정 — 임의 확장 금지)

- 공정: **집합공정 1개만** (다른 공정 없음, BOM 전개 없음 — 출하계획 파일의 품목코드가 곧 생산 품목코드)
- 설비: **집합01호기 ~ 집합10호기** (10대)
- 품목: **7000260, 7000320, 1600190, 1900160, 1900190, 2400190, 3000173, 3700260** (8종)
- 고객사: **고객사A, 고객사B, 고객사C** (3곳)

## ⚠️ 익명화 절대 규칙 (모든 산출물에 최우선 적용)

- 실제 고객사명·회사명·사람 실명·사내 URL·기존 폴더 ID를 코드, 데이터, 시트, 알림 메시지, 로그 어디에도 절대 쓰지 않는다.
- 고객사 표기는 `고객사A` `고객사B` `고객사C` 만 사용한다.
- 설비 표기는 `집합01호기`~`집합10호기` 만 사용한다. (실제 공정명을 붙인 호기 표기 금지)
- 검사는 `/anon-check` 스킬(스크립트)로 전수 실행한다. Edit/Write마다 훅이 자동으로 같은 검사를 돌리며, 훅이 위반을 알리면 다음 작업 전에 즉시 고친다.
- 위반 가능성이 있는 텍스트를 발견하면 즉시 사용자에게 알린다.

## 개발 환경

- 언어: **Google Apps Script (V8)** / 데이터: Google Sheets 전용 (출고계획도 판독 파트가 Google 스프레드시트로 준다). 파일 탐색은 **확장자·MIME·폴더명이 아닌 파일명 패턴**으로 한다. xlsx가 들어오는 경우만 Drive 고급 서비스로 임시 변환해 읽는다(보조 경로)
- 로컬 편집 폴더: `split/` — **Code.gs**(진입점·CFG·데이터로드·트리거·onOpen 메뉴), **Planner.gs**(호기 배정 → 작업목록 배열 반환. 시트 서식 코드 금지), **Scheduler.gs**(시간 시뮬레이션), **Publisher.gs**(작업목록 → 결과 시트 탭 렌더링. 모든 뷰는 여기서만), **Utils.gs**(날짜·변환·시트/Drive 헬퍼·notify_)
- 스크립트는 기준정보 스프레드시트(파일명 `기준정보`)에 **바인딩(container-bound)** 된 프로젝트다 — 담당자가 작업하는 입력 파일이라 단순 `onOpen()`으로 [▶ 생산계획] 메뉴가 여기에 생기고, 기준정보는 복사·재생성될 일이 없어 스크립트 거처로 안전하다. 결과 파일에는 스크립트가 없다(백업 사본에도 안 딸려감). 결과 파일 쓰기는 `openById(CFG.RESULT_SS_ID)`로 한다. clasp는 바인딩 스크립트도 scriptId 기준으로 동일하게 push한다.
- 배포: clasp — **gdrive 에이전트에게 위임** (직접 clasp push 금지)
- 샘플 데이터: `더미데이터/기준정보.xlsx`(탭 11개 — 출하계획·실적 없음)를 Drive에 올려 Sheets로 변환한 것이 기준정보 스프레드시트. 출고계획은 `더미데이터/발주원본/9월_출고계획(통합).xlsx`를 프로젝트 루트(아무 하위 폴더도 가능)에 올려 Sheets로 변환한 것 — 파일명 `9월_출고계획(통합)`만 유지하면 된다. 출하계획 스프레드시트는 올리지 않는다(코드가 만든다). 실적은 `더미데이터/실적/생산실적.xlsx`·`출하실적.xlsx`를 루트 아래 아무 폴더에 올린 것 — 파일명 앞부분 `생산실적`·`출하실적`만 유지하면 된다.

## Drive 구조와 CFG

```
[프로젝트 루트]/   ← 폴더 자체를 "링크가 있는 모든 사용자 — 뷰어"로 공유. 심사위원 배포 링크 = 이 폴더 하나
│                     (발주원본 → 출하계획 → 생산계획 전 과정이 한 폴더에서 보임. 하위 파일·폴더 전부 권한 상속)
├── 📗 기준정보             CFG.MASTER_SS_ID   [자동] 비어 있으면 스크립트가 바인딩된 파일 자신. 기준정보 11탭(탭 명세 아래) — **출하계획·출고계획·실적 없음**. **스크립트 바인딩 위치** ([▶ 생산계획] 메뉴)
├── 📗 X월_출고계획(통합)   (CFG 없음)         [외부 입력] 판독 파트가 두는 출고계획 스프레드시트. **루트 아래 어느 폴더에 있어도 되고 폴더명은 정해져 있지 않다** — 코드는 `CFG.ORDER_ROOT_FOLDER_ID`(비어 있으면 기준정보의 부모 폴더 = 프로젝트 루트) 아래를 재귀 탐색해 **파일명 정규식 `/^\d{1,2}월_출고계획\(통합\)/`** 으로 찾는다(확장자·MIME 무관). 옮기거나 이름을 바꾸지 않는다(판독 파트가 계속 편집하는 파일)
├── 📗 생산실적 / 출하실적  (CFG 없음)         [외부 입력] 실적 시스템에서 **매일 새로 올려두는 파일**. 루트 아래 어느 폴더든 되고,
│                                              파일명 `/^생산실적/`·`/^출하실적/` 패턴으로 찾는다(같은 패턴 여러 개면 최신 수정본). 읽기만 한다
├── 📗 출하계획             CFG.SHIP_SS_ID     [자동 생성] 비어 있으면 스크립트 속성 → 없으면 첫 변환 때 같은 폴더에 생성. 탭 [출하계획] 4열(품목코드·고객사·출하일·출하량(kg)). convertOrderToPlan()의 산출물이자 **판독 파트 인터페이스**(판독 확정 행도 여기에 append). 사람이 미리 만들지 않는다
├── 📗 생산계획              CFG.RESULT_SS_ID   [자동 생성] 비어 있으면 첫 실행 때 기준정보와 같은 폴더에 생성, ID를 스크립트 속성에 저장 후 계속 재사용(링크 불변). 실행마다 탭 내용만 덮어씀
├── 📁 일별생산계획/        CFG.BACKUP_FOLDER_ID      [자동 생성] 동일. 실행마다 결과 사본 "YYMMDD-HHmm_생산계획" — 루트 폴더 공유를 상속해 [이력] 사본URL이 바로 열림
└── 📁 작업지시서/          CFG.WORKORDER_FOLDER_ID   [자동 생성] **호기별 작업지시 파일 10개**(`집합01호기 작업지시` … `집합10호기 작업지시`). 각 호기 반장에게 자기 파일 링크·QR만 주면 되고 다른 호기 일정·재고·기준정보는 보이지 않는다. 파일 ID를 스크립트 속성 `WORKORDER_SS_JSON`에 호기별로 저장해 링크가 바뀌지 않는다. 결과 파일의 호기 탭 10개와 같은 렌더러(`writeMachineOrder_`)를 쓴다
```

- **ID 자동 해결(사람이 입력할 필수 ID 없음)**: `MASTER_SS_ID`가 비어 있으면 바인딩 컨테이너(`getActiveSpreadsheet()`)를 쓴다. `SHIP_SS_ID`·`RESULT_SS_ID`·`BACKUP_FOLDER_ID`가 비어 있으면 스크립트 속성에서 찾고, 속성에도 없으면 **첫 실행 때만** 기준정보와 같은 폴더에 만들어 속성에 저장한다 — 두 번째 실행부터는 절대 새로 만들지 않는다(알림에 공유된 링크가 계속 살아 있어야 함). `ORDER_ROOT_FOLDER_ID`가 비어 있으면 기준정보 파일의 부모 폴더(프로젝트 루트)를 탐색 기준으로 쓴다. CFG에 값이 있으면 항상 그것을 우선한다. 출하계획 파일이 아직 없고 출고계획 파일도 못 찾으면 runAll은 "출하계획 없음 — `X월_출고계획(통합)` 파일을 찾지 못함"으로 중단한다(기준정보만으로는 계획을 만들 수 없다).
- 기준정보 파일은 코드가 만들지 않는다(바인딩된 파일 자신). 출하계획 파일·결과 파일·일별생산계획/ 폴더는 없을 때 최초 1회만 만들고, 이후에는 탭이 없으면 그 탭만 만든다.
- **심사위원 공유 = [프로젝트 루트]/ 폴더 링크 하나** (뷰어). 더미데이터(익명화 완료)라 폴더 전체 공개가 가능하다. 실운영 전환 시에는 기준정보(CAPA·원가 포함)를 공유 범위에서 제외해야 한다. **기준정보·CAPA·원가는 결과 파일에 절대 쓰지 않는다.**

## 계획 로직 규칙

1. 절대차단: [안되는품목]의 (품목, 호기) 조합은 어떤 경우에도 배정 금지. optional 탭으로 취급 금지 — 없으면 에러.
2. 우선설비: [우선순위] 지정 호기를 우선 배정하되, 대기가 48h를 넘으면 차순위 호기로 폴백.
3. 동일규격 우선: 현재 같은 품목이 걸린 호기([설비규격교체현황] 기준)는 교체시간 0으로 우선하되, 대기 168h 초과 시 포기.
4. 그 외에는 가장 빨리 비는 호기에 배정.
5. 품목별 [최대설비가동수]를 초과해 동시 가동하지 않는다.
6. 주말과 [휴무] 탭의 날짜는 생산하지 않는다 (시간 계산에서 skip).
7. 기초재고를 먼저 차감하고 부족분만 생산한다. **같은 품목·같은 출하일은 고객사와 무관하게 하나로 묶어** 생산한다(현장은 고객사별로 나눠 돌리지 않고 같은 규격을 몰아서 만든다). 정렬은 출하일 빠른 순 → 동일 출하일은 품목코드 순. 생산량은 품목별 CAPA `중량(KG)`(보빈 1개) 배수로 **올림**해 배정한다 — 수요가 배수가 아니어도 보빈 단위로 생산하며, 올림분은 재고로 남는다.
   ※ [출하우선순위]는 **출하 단계**의 순서이지 생산 순서가 아니다. 묶은 작업의 고객사 열에는 `고객사A·고객사B`처럼 함께 표기한다.
8. 규격교체 시 1.5시간, 계획 첫날은 가동준비 3시간을 점유시간에 더한다.
8-1. **규격교체 회피 우선(규칙 2·3·4보다 앞선다)**: 교체 없이(현재 걸린 규격 그대로) 납기 안에 끝낼 수 있는 호기가 있으면, 더 빨리 끝나는 다른 호기가 있어도 그 호기를 쓴다. 교체는 그 자체로 손실이고, 교체한 호기를 원래 품목으로 되돌릴 때 또 한 번 들어 손실이 두 배가 되기 때문이다. 납기가 없는 작업(적정재고 보충)에는 적용하지 않는다.
8-1-b. **납기 우선(8-1의 단서)**: 교체 없이 납기 안에 끝낼 수 있는 호기가 **하나도 없으면**, 교체를 감수하더라도 납기를 지킬 수 있는 호기만 후보로 남기고 그 안에서 규칙 8-2·2·3·4를 적용한다. 납기를 지킬 후보가 아예 없으면(능력 부족) 전체 후보를 그대로 쓰고 납기위험으로 보고한다. 8-1이 "교체 없이 **납기 안에**"를 조건으로 하므로, 납기를 못 지키는 무교체 호기보다 납기를 지키는 교체 호기가 낫다. (전문가 교차검증 반영 — 이 단서가 없으면 규칙 3이 전담 호기만 계속 골라 납기를 놓친다)
8-2. **전담 호기 예약**: [설비규격교체현황]의 초기 규격은 "이 호기가 이 품목을 맡는다"는 뜻으로 본다. 초기 규격이 다른 품목이고 그 품목에 아직 수요가 남아 있는 호기는 후순위로 미룬다(그 호기를 뺏으면 뺏은 쪽·밀려난 쪽 양쪽에 교체가 생긴다). 기다림이 `DEDICATED_WAIT_LIMIT_HR`을 넘으면 예약을 푼다. 쓸 호기가 그것뿐이면 그때는 쓴다.
8-3. **청크는 보빈(만권) 단위로 자른다**: 72시간(MAX_CHUNK_HOURS) 초과 작업을 나눌 때 시간 비율로 kg을 쪼개면 마지막 조각이 보빈 1개에 못 미치는 자투리가 되어 현장에 내릴 수 없다. 72시간 안에 들어가는 **보빈 개수**만큼만 담고 나머지를 다음 조각으로 넘긴다. 그래서 모든 조각의 생산량이 보빈 중량의 정수배이며, 조각당 시간은 72시간에 못 미칠 수 있다.
9. **Payoff 제약**: 가닥수 37 이상 품목(3700260)은 **Payoff수 2 이상 호기에서만** 생산 가능하다. 현 설비 구성에서 2-payoff 호기는 **집합09·10호기 2대뿐**이다. [집합설비현황]의 Payoff수로 검증하며, 기종(적용설비) 매칭과 별개로 독립 체크한다.
10. **처리 결과가 0건이면 절대 "완료"로 넘기지 않고 경고를 발송한다.**
11. **실적 반영 (기준일 규칙)**: 기준일 = [설정] 탭 `AS_OF_DATE`(비어 있으면 오늘). **실적이 존재하는 구간(기준일 당일 오전 실적 포함)** 은 [생산실적]·[출하실적] 값을 쓰고 계획값을 쓰지 않는다. 계획 시작 재고 = 기초재고 + Σ생산실적 − Σ출하실적(실적 파일 전체 합산)이며, 신규 생산계획은 기준일부터(당일 실적 이후 잔여 시간부터) 배정한다. 출하계획 대비 미출하 잔량(계획 − 실적 > 0)은 기준일 이후 첫 근무일 출하로 이월하고 [요약]에 "이월 N건"으로 표시한다. 실적이 있는 작업의 상태는 `완료`. 실적 파일이 없거나 비어 있으면 이 규칙은 통째로 건너뛴다(기존 동작 그대로). 더미데이터는 기준일 2026-09-04(데모 당일), 실적은 9/1~9/4 오전까지다. **출고계획은 판독 파트 산출물이므로 우리 파트에서 작성·정합을 맞추지 않는다** — 동봉 샘플 출고계획으로 돌릴 때만 실적 구간의 출하계획 = 출하실적이 일치해 이월 0건이고, 판독 파트의 실제 출고계획에서는 이월이 잡히는 것이 정상이다(집계 버그가 아니다).
    실적 두 파일은 **현장 실적 시스템 내보내기 양식 그대로(보빈/LOT 1개 = 1행)** 이므로 반드시 집계해서 쓴다: 생산실적은 `품목코드 × 실적일자(× 작업호기)`로 **양품수량**을 합산, 출하실적은 `품목코드 × 출고일자(× 납품처=고객사)`로 **수량(KG)**을 합산한 뒤 출하계획의 `(품목코드, 출하일, 고객사)`와 대조한다. 출하계획에 없는 (품목, 출고일, 고객사) 출고는 이월분 출하로 보고 앞선 미출하 잔량에서 차감한다. 날짜·시각 열은 텍스트일 수 있으니 `toDate_`로 파싱하고, 품목코드는 `normalizeItemCode_`로 통일한다.
12. **적정재고 보충**: 납기 수요 배정이 모두 끝난 뒤, 계획 구간 말 예상 재고가 [적정재고] 값 미만인 품목은 부족분을 보빈(CAPA 중량(KG)) 배수로 올림해 **여유 시간에만** 추가 배정한다. 보충 생산은 납기 수요 작업을 뒤로 밀지 않으며, 능력이 부족해 못 채우면 [요약]에 "적정재고 미달 품목"으로 표시만 한다. [적정재고]에 없는 품목은 대상이 아니다. (더미데이터 2026-09-03 실측: 3700260 기준일 재고 4,415 < 적정 10,000, 1900190 417 < 적정 2,000 → **두 품목 모두** 여유 시간에 보충 생산이 잡히는 것이 정상)

- 기준 탭의 품목코드·호기 열은 텍스트 서식이지만 **CAPA 탭과 실적 파일의 품목코드는 숫자로 들어온다** — 코드는 어느 쪽이든 `normalizeItemCode_`로 문자열 통일한다 (앞자리 0 소실·`7000260.0` 사고 방지).
- CAPA 탭과 생산실적·출하실적 두 파일은 **실제 시스템의 파일 양식을 열 구성까지 그대로** 쓴다(나중에 실데이터를 그대로 붙일 수 있게). 필요한 열만 헤더 이름으로 골라 읽고, 나머지 열은 무시한다. 열 순서에 의존하지 않는다.
- 실적 두 파일의 날짜·시각(계획일자·실적일자·작업일시·출고일자·시간)은 **텍스트**로 들어온다 — `toDate_`가 문자열·Date 둘 다 받아야 한다.
- CAPA는 `적용설비` 단위, 설비현황이 `호기 → 적용설비`를 매핑한다(현 구성은 전 호기 `집합기` 단일 기종 — 전 호기 kg/hr 동일). 호기별 시간당 생산량 = 해당 호기의 적용설비 기준 kg/hr.
- **출하 단위 원칙(더미데이터)**: 한 번의 출하(품목×출하일×고객사)는 **7000260·7000320·1900160·1900190이 5~10보빈**, 그 외 품목은 **최소 2보빈**이며, **한 고객사에 하루 나가는 총량은 4,500kg(트럭 1대)을 넘지 않는다**. 묶음을 못 채운 잔량은 출하하지 않고 재고로 남긴다.
- **보빈 단위 원칙**: 기초재고·실적은 보빈(1행=1보빈) 단위이고, **계획 생산량은 규칙 7대로 보빈 배수로 올려** 배정한다. 단 **고객사 출고계획(→출하계획) 수량은 보빈 배수가 아닐 수 있다** — 실데이터에서 정상이므로 배수 검증을 하지 않는다(더미데이터만 전 수량이 배수로 만들어져 있다). 수요가 배수가 아니면 올림분이 재고로 남는다.

## 실적 파일 (`CFG.ACTUAL_PROD_PATTERN` · `ACTUAL_SHIP_PATTERN`) — 기준정보와 별개, 매일 갱신

생산실적·출하실적은 **실적 시스템에서 매일 새로 내려받아 올리는 파일**이라 기준정보 탭에 두지 않는다. 출고계획과 같은 방식으로 **탐색 루트 아래 어느 폴더에 있든 파일명 패턴으로 찾고**(`/^생산실적/`, `/^출하실적/` — 확장자·MIME·폴더명 무관, xlsx면 Drive 고급 서비스로 임시 변환해 읽고 즉시 삭제), 같은 패턴이 여럿이면 **가장 최근에 수정된 파일**을 쓴다. 파일 안에서는 탭 이름이 `생산실적`/`출하실적`이면 그 탭을, 없으면 **첫 탭**을 읽는다(내보내기 시트명이 제각각일 수 있음).

| 파일 | 컬럼 | 구분 |
| ---- | ---- | ---- |
| 생산실적 | LOTNO · **품목코드** · 품목명 · **작업호기** · **양품수량**(kg) · 불량수량 · 단위 · 조장 · 계획일자 · **실적일자** · 작업자 · 작업일시 · 바코드 — 실적 시스템 내보내기 양식 그대로(13열), **보빈(LOT) 1개 = 1행**. 계획에 쓰는 열은 굵은 4개, 반드시 품목×실적일자로 합산. 날짜는 텍스트 `YYYY-MM-DD` | 있으면 적용 (규칙 11) |
| 출하실적 | 품목명 · **품목코드** · 규격 · LOT · 바코드 · 수량(M) · **수량(KG)** · 보빈(KG) · **출고일자** · 시간 · **납품처**(=고객사) — 출하 시스템 내보내기 양식(11열), 보빈 1개 = 1행. 계획량·비고 열 없음 → 출하계획과 (품목코드, 출하일, 고객사)로 대조해 미출하 잔량을 구한다. 출고일자는 텍스트. 실데이터 이식 시 헤더가 `품명`·`품번`으로 올 수 있으니 폴백 인식 | 있으면 적용 (규칙 11) |

- 두 파일이 **없으면 규칙 11을 통째로 건너뛴다**(전 구간 계획 모드). 한쪽만 있어도 있는 쪽만 반영한다.
- 파일의 `lastUpdated`를 스크립트 속성 `ACTUAL_PROCESSED_JSON`에 기록해, **새 파일을 올리거나 덮어쓰면 트리거가 감지**해 재계획한다(사유 `실적 반영: 파일명`). 실행이 끝나면 반영이력을 갱신해 같은 파일로 두 번 돌지 않는다.
- 실적 파일은 **읽기만** 한다 — 옮기거나 이름을 바꾸거나 내용을 쓰지 않는다.

## 출하계획 스프레드시트 (`CFG.SHIP_SS_ID`, 자동 생성 — 기준정보와 별개 파일)

탭 `출하계획` 1개, 컬럼 `품목코드 · 고객사 · 출하일 · 출하량(kg)`. 이 파일이 계획 엔진의 수요 입력이다. 사람이 만들거나 편집하지 않는다.

- **기본 입력 경로 = 출고계획 변환 `convertOrderToPlan()`**: 탐색 루트(`CFG.ORDER_ROOT_FOLDER_ID` 또는 기준정보의 부모 폴더) 아래를 **재귀적으로** 돌며 **파일명이 `/^\d{1,2}월_출고계획\(통합\)/`에 맞는 파일**을 전부 찾는다(폴더명·확장자·MIME 무관, 일별생산계획/·결과 파일은 이름이 다르므로 걸리지 않음). Google 스프레드시트면 `SpreadsheetApp.openById`로 첫 탭을 바로 읽고, xlsx MIME이면 Drive 고급 서비스로 임시 변환해 읽는다(고급 서비스가 없으면 그 파일만 건너뛰고 경고). 읽은 표(가로 날짜형 `품목코드·구분(고객사)·발주량·합계·날짜열…`)를 세로 melt(0·빈 셀 제외, 품목코드 문자열 통일)하고, 출하계획 파일이 없으면 만들고 [출하계획] 탭에 **(품목코드, 고객사, 출하일) 키로 upsert**한다 — 같은 키는 출하량 덮어쓰기, 새 키는 추가, 그 후 출하일→품목코드→고객사 순 정렬. 같은 파일을 두 번 처리해도 결과가 같아야 한다(멱등). **출고계획 파일은 옮기거나 이름을 바꾸지 않는다** — 판독 파트가 계속 편집하는 파일이다. 대신 스크립트 속성에 `처리이력: {파일ID: lastUpdated}`를 저장해 두고, `getLastUpdated()`가 저장값과 다를 때만 다시 읽어 upsert한다. 변환 0건이면 경고만. 임시 변환 파일은 try/finally로 반드시 삭제.
- **외부 소스 폴더 동기화 (선택 — 판독 파트가 루트 밖 폴더를 쓸 때)**: [설정] 탭 `ORDER_SOURCE_FOLDER_ID`(폴더 URL 또는 ID, `CFG.ORDER_SOURCE_FOLDER_ID`가 있으면 그것을 우선)가 지정되면, 변환 전에 `syncOrderFiles_()`가 그 폴더 아래를 재귀 탐색해 파일명 패턴에 맞는 파일 중 **lastUpdated가 바뀐 것만** 프로젝트 루트의 `출고계획/` 폴더로 복사해 온다. 복사본이 이미 있으면 파일을 새로 만들지 않고 **첫 탭 내용만 덮어써** 복사본 URL을 유지한다(동기화 이력 `ORDER_SYNC_JSON {소스ID:{copyId,stamp}}`). **원본 폴더·파일은 읽기만 하고 절대 이동·수정하지 않는다.** 소스 미지정이면 이 단계는 통째로 생략(기존 동작). 소스가 프로젝트 루트와 같으면 중복 복사를 막기 위해 생략한다.
- **판독 파트 경로**: 판독 파트가 검수 화면에서 확정한 발주를 같은 파일 [출하계획] 탭에 4열 행으로 append한다. 이 파트는 그 파일을 읽고 변경을 감지해 재계획할 뿐 판독 로직을 갖지 않는다. 판독 화면이 없을 때의 임시 입력은 탭에 행을 직접 붙여넣는 것(또는 `demoAddOrder()`)이다.

## 산출물 — 결과 스프레드시트 (`CFG.RESULT_SS_ID`, 고정 ID)

결과 파일이 아직 없으면(최초 1회) 자동 생성해 스크립트 속성에 ID를 저장한다. 이후 실행마다 아래 탭의 **내용만 덮어쓴다**(`clearContents` 후 배치 setValues). 파일을 삭제·재생성하지 않는다 — 링크·QR이 바뀌면 안 된다. 실행 후 파일 사본을 일별생산계획/ 폴더에 `YYMMDD-HHmm_생산계획`으로 저장하고, 그 사본 URL을 [이력] 행에 기록한다. 이 사본이 기존 운영의 일일생산계획 파일에 해당하며, 파일명에 실행 시각이 들어가므로(압출 생산계획의 `압출생산계획_YYYYMMDD_HHMM.xlsx`와 같은 방식) 하루에 여러 번 실행해도 덮어쓰지 않고 실행본이 전부 남는다.

**기준정보 파일**에 커스텀 메뉴 **[▶ 생산계획]**을 단다(스크립트가 기준정보에 바인딩 → 메뉴는 단순 `onOpen()` 함수만으로 뜬다. 설치형 onOpen 트리거가 불필요하다는 뜻일 뿐, 자동 재계획용 설치형 트리거 2개(onChange·1분)는 별개로 `installTrigger()`에서 등록한다 — §트리거·자동 재계획) — 항목: `지금 재계획`(runAll('수동')) · `최신 계획 열기`(결과 파일 링크) · `호기별 작업지시서 링크`(작업지시서/ 폴더의 호기별 파일 10개 링크 — 현장 배포·QR용) · `이전 계획 보기`(결과 파일 [이력] 탭 링크 — 사본URL 클릭). 링크는 `SpreadsheetApp.getUi()` 다이얼로그의 앵커로 연다. 메뉴 실행은 기준정보 편집 권한자용이다.
결과 파일과 그 백업 사본에는 스크립트가 없으므로, 뷰어 링크로 여는 심사위원·현장은 열람만 가능하고 옛 사본에서 옛 코드가 실행될 위험도 없다(사본 가드 불필요).

탭 순서(왼쪽부터): **통합 · 집합01호기 ~ 집합10호기 · 재고흐름 · 요약 · 작업목록 · 일별생산 · 오류 · 이력** (총 18개). 사람이 보는 탭을 앞에, 데이터·로그 탭을 뒤에.

| 탭         | 내용 |
| ---------- | ---- |
| 통합       | 기존 운영의 월 통합 생산계획 양식. 행=(호기×품목) 블록당 3행(생산량(KG)·조장(m)·생산시간(Hr)), 열=`호기·품목코드·규격·만권조장·구분·합계` + 계획월 1일~말일 날짜(`9/1(화)` 요일 표기). 주말·[휴무] 열은 헤더 포함 연빨강, 값 없는 날 0, 가운데 정렬·격자 테두리. 신규/변경 셀은 연주황. [일별생산]에서 그림 |
| 집합01호기 ~ 집합10호기 | **호기별 작업지시 탭 10개** (아래 "호기 탭 규격"). [작업목록]을 호기로 필터 |

| 요약       | 대상월, 품목별 총 생산/총 출하/월말 재고, 일 평균 생산량, 일 최대 출하량(날짜), 규격교체 총 횟수, 납기위험 품목(최초 음수일), 이월 N건, 적정재고 미달 품목(규칙 12에서 못 채운 품목), 호기별 가동률(%) |

### 호기 탭 규격 (집합01호기 ~ 집합10호기, 렌더러 하나로 10개 생성)

- 1행: `집합09호기 작업지시 | 계획ID YYMMDD-HHmm | 갱신 YYYY-MM-DD HH:mm | 이번 달 작업 N건 · 총 Mkg · 교체 K회` (한 줄, 병합 없이 셀 4개)
- 3행 헤더, 4행부터 작업 1건 = 1행: `순번 · 품목코드 · 규격 · 생산량(kg) · 조장(m) · 보빈수 · 예상 종료시간 · 소요시간(h) · 출하일 · 교체 · 상태` (고객사 · 청크는 현장에서 쓰지 않아 뺐다 — 청크는 같은 품목이 연달아 나오는 것으로 알 수 있고 두 값은 [작업목록] 탭에 남아 있다. 교체는 Y/N 열과 행 노란색으로 함께 표시한다) — [작업목록]에서 그 호기만 필터, 순번 순. 대회 중엔 전 기간 표시(HORIZON 미적용).
  규격·조장·보빈수는 [CAPA] 조인 (조장(m) = 생산량 × 만권조장(조장(m)) ÷ 중량(KG), 보빈수 = 생산량 ÷ 중량(KG)). **시작일시는 싣지 않는다** — 현장은 순번대로 이어서 작업하므로 "예상 종료시간"만 본다.
- 행 배경: 교체=Y 노란색 > 상태 신규/변경 주황 > 확정·완료 회색. 헤더 3행 고정, 품목코드 텍스트, 일시 Date, 헤더·데이터 격자 테두리에 가운데 정렬.
- 작업이 없는 호기도 탭은 만들고 1행에 "이번 달 배정 없음"을 쓴다.
- 검증: 10개 탭 kg 합 = [작업목록] 총 kg, 각 탭에 다른 호기 작업이 섞이지 않음, 탭 순번이 [작업목록]과 일치.
- 시트 I/O: 탭당 setValues 1회 + setBackgrounds 1회. 10개 탭 합쳐 30초 이내가 목표.

### 작업목록 데이터 모델 (단일 진실 원천)

계획 결과는 반드시 아래 컬럼의 **작업목록** 배열/탭으로 먼저 만들고, 호기별 피벗·재고흐름·요약 등 **모든 뷰는 [일별생산]과 [작업목록]을 읽어서만** 그린다. 시뮬레이션 결과 객체를 뷰 코드가 직접 참조하지 않는다.

| 컬럼 | 형식 | 비고 |
| --- | --- | --- |
| 계획ID | `YYMMDD-HHmm` | runAll 실행 시각. 재계획 diff·이력 키 |
| 호기 | 집합01호기~집합10호기 | 현장 배포 단위 키 |
| 순번 | 정수 | 호기 내 시작일시 순 |
| 품목코드 · 규격 · 고객사 | | 규격은 [CAPA] 탭에서 조인 (현장은 규격으로 소통) |
| 출하일 | 날짜 | 이 작업이 채우는 가장 빠른 출하 건 |
| 시작일시 · 종료일시 · 소요(h) | | 소요 = 생산량 ÷ kg/hr (+교체 1.5h) |
| 생산량(kg) | 숫자 | |
| 교체 | Y/N | 직전 규격과 다르면 Y |
| 청크 | `n/m` | 72h 분할 시 |
| 상태 | 계획 · 확정 · 변경 · 신규 · 완료 | 최초 계획은 전부 `계획`. 재계획(replanFromToday)에서 채움. `완료` = 기준일 전 실적으로 대체된 구간 |

시트 형식 규칙: 헤더는 1행에만, 병합 셀 금지, 한 행 = 한 작업, 시작일시·종료일시·출하일은 문자열이 아닌 **Date 값**. (후속 단계에서 AppSheet·웹앱이 이 탭을 그대로 데이터 소스로 물 수 있어야 한다.)

### 파생 테이블 — [일별생산] (일 단위 뷰의 유일한 원천)

작업목록은 **작업 단위**(여러 날에 걸침)이고 재고흐름·호기별 피벗·요약은 **일 단위**다. 그 사이를 잇는 표를 반드시 만든다. Publisher가 작업목록에서 결정적으로 계산하며, 모든 일 단위 뷰는 이 표만 읽는다.

| 컬럼 | 비고 |
| --- | --- |
| 계획ID · 호기 · 순번 · 품목코드 | 작업목록 키 그대로 |
| 날짜 | Date 값 |
| 가동시간(h) | 그 날짜에 실제 생산한 시간 (교체 1.5h·첫날 준비 3h 제외) |
| 생산량(kg) | 작업 kg × (그 날 가동시간 ÷ 작업 총 가동시간). 반올림 오차는 마지막 날에 몰아 작업별 합계 = 작업 kg 보장 |

규칙:
- 일일 생산량 = [일별생산]을 품목×날짜(재고흐름) 또는 호기×날짜(피벗)로 합산한 값. 작업 kg을 시작일에 몰아넣지 않는다.
- 일일 출하량 = 출하계획 파일 [출하계획] 탭을 품목×날짜로 합산한 값.
- 재고흐름: `재고(D) = 재고(D−1) + 일별생산(D) − 출하(D)`, 첫 열은 기초재고. 당일 생산분은 당일 출하에 사용 가능(일 마감 기준). 음수 = 납기위험.
- 실적이 있으면 기준일 전 열은 [일별생산]·[출하계획] 대신 **[생산실적]·[출하실적]** 값을 쓰고, 해당 열 헤더를 회색 배경으로 구분한다(실적 구간). 기준일 열부터가 계획이다.
- 검증: Σ일별생산 = Σ작업목록 생산량(품목별·호기별 모두 일치), 호기별 하루 가동시간 ≤ 24h(첫날 21h). 어긋나면 결과를 내지 않고 [오류] 탭에 기록 후 에러.

## 갱신 감지·트리거 규칙

- `installTrigger()`가 트리거 2개를 등록한다: ① 기준정보 파일 대상 **설치형 onChange 트리거** — 기준정보 변경 즉시 감지 (스크립트가 기준정보에 바인딩되어 있어 가능) ② **1분 시간 기반 트리거** — 출고계획 파일 신규/수정 감지(파일명 탐색 + lastUpdated 비교) + 출하계획 파일 변경 감지(별개 파일이라 onChange로 못 잡는다) + onChange가 놓친 경우 대비. 둘 다 `checkAndRunOnUpdate()` 하나로 들어간다. 트리거는 push만으로 생기지 않는다. ([▶ 생산계획] 메뉴는 단순 onOpen이라 별도 트리거가 필요 없다)
- onChange는 서식 변경 등에도 발생하므로, **실제 재계획 여부는 아래 해시 비교가 결정**한다 — 내용이 진짜 달라졌을 때만 runAll. 변경이 없으면 아무것도 하지 않는다. 연속 이벤트 중복은 LockService가 막는다.
- `checkAndRunOnUpdate()`는 아래 순서로 검사해 하나라도 해당하면 실행한다:
  1. **탐색 루트 아래에 처리이력에 없거나 lastUpdated가 바뀐 `X월_출고계획(통합)` 파일이 있다** → `convertOrderToPlan()`으로 출하계획 파일 upsert → 처리이력 갱신 → `runAll()`. 사유 `출고계획 반영: 파일명`
  1-2. **실적 파일(생산실적·출하실적)이 새로 올라왔거나 lastUpdated가 바뀌었다** → `runAll()`. 사유 `실적 반영: 파일명`. 반영이력은 `ACTUAL_PROCESSED_JSON`
  2. **출하계획 파일 [출하계획] 탭의 내용 해시**가 스크립트 속성 값과 다르다(판독 파트 append·수동 편집) → `runAll()`. 사유 `출하계획 갱신(판독 확정)`
  3. **기준정보 11탭의 내용 해시**(헤더 포함)가 저장값과 다르다 → `runAll()`. 사유 `기준정보 변경`. 해시는 파일별로 따로 저장해 사유를 구분한다
- 실행이 끝나면 새 해시(출하계획·기준정보 각각)를 저장한다. convertOrderToPlan이 출하계획 파일에 쓴 뒤에는 그 해시도 갱신해 같은 변경으로 두 번 실행되지 않게 한다. 결과 파일에 쓰는 것은 어느 해시에도 영향이 없으므로 자기 자신을 다시 깨우지 않는다. **[오류]·[이력]은 결과 파일에만 쓴다** (기준정보·출하계획 파일에 쓰면 무한 루프).
- 중복 실행 방지: `LockService.getScriptLock()` 30초 대기, 못 잡으면 skip 후 [이력]에 "skip(실행 중)" 기록.
- 트리거 사유(출고계획 반영: 파일명 / 출하계획 갱신(판독 확정) / 기준정보 변경 / 수동)를 [이력]과 알림에 남긴다.
- **알림 메시지 형식 (기존 사내 생산계획 시스템의 notifyGoogleChat_ 동작 그대로 재현)**: `notifyGoogleChat_(label, bodyText)` —
  - 라벨: 수동 `👤 [수동실행]` · 자동 `🤖 [자동실행]` · 오류 `👤 [수동실행 오류]`/`🤖 [자동실행 오류]`
  - 색상 결정: 라벨 문자열에 `'오류'` 포함 → 빨강 `#FF0000`, `'자동실행'` → 파랑 `#0000FF`, `'수동실행'` → 초록 `#008000`, 그 외 검정. 라벨은 `<font color="…"><b>라벨</b></font>`로 감싼다
  - 본문 변환: `\n` → `<br>`, 본문 속 URL은 정규식 `/(https?:\/\/[^\s<]+)/g`로 `<a href="URL">바로 열기</a>` 앵커로 자동 치환
  - 전송: `CHAT_WEBHOOK_URL`(스크립트 속성, 없으면 기준정보 [설정] 탭 `WEBHOOK_URL`)로 `cardsV2` 카드(sections → widgets → textParagraph.text) POST. 둘 다 미설정이면 에러 대신 Logger 경고 후 **알림 생략**, 전송 실패도 try/catch로 runAll을 죽이지 않는다
  - 성공 메시지: `생산계획 생성이 완료되었습니다. (yyyy-MM-dd HH:mm)` — 자동실행이면 둘째 줄에 감지 사유(예: `출하계획 파일 변경이 감지되어 실행되었습니다.`) + 요약 한 줄(총 N건·총 Mkg·교체 K회·납기위험) + `\n\n📄 생성된 파일:\n` 아래 `YYMMDD-HHmm_생산계획: {사본URL}`과 `최신 계획: {고정 결과 파일 URL}` (URL은 "바로 열기"로 표시됨)
  - 실패 메시지: `생산계획 실행에 실패했습니다. (yyyy-MM-dd HH:mm)\n{단계}\n{오류 메시지}`
  - 폴백 채널(텔레그램·메일)은 색·앵커 미지원이라 아이콘+라벨과 원문 URL 텍스트로만 보낸다.

## 현장 배포 확장 규칙 (대회 후 설비별 계획 배포 대비 — 상세: 06_설비별_계획_현장배포_설계.md)

- 결과 파일이 고정 ID이므로 대회 중 심사위원·팀에 공개하는 링크는 결과 파일 링크 하나다. 호기 탭 10개도 이 파일에 있다.
- 후속(현장 배포)은 같은 `renderMachineTabs_` 렌더러를 별도 파일(`CFG.PUBLISH.DIST_SPREADSHEET_ID`, 재고·기준정보 비노출)에 `HORIZON_DAYS`(3일)만 잘라 그리고 탭 URL을 QR로 뽑는 것이다. 대회 중엔 ID를 비워둔다.
- 뷰 추가는 Publisher.gs에 렌더러 함수 추가 + `CFG.PUBLISH.VIEWS`에 이름 추가로 끝나야 한다. 코어(Planner/Scheduler) 수정 금지.
- `CFG.PUBLISH = { DIST_SPREADSHEET_ID:'', VIEWS:['integrated','machineTabs','inventory','summary','workOrderFiles'], HORIZON_DAYS:3, BRIEFING_HOUR:7 }` 자리를 만든다.

## 코딩 원칙

- GAS 6분 실행시간 제한을 항상 의식한다.
- 시트 I/O는 반드시 `getValues()` / `setValues()` 배치로 처리한다. 셀 단위 루프 금지. 탭 하나 = 읽기 1회, 쓰기 1회가 기본.
- 스프레드시트 ID·폴더 ID·탭 이름·품목/설비/고객사 목록 등 설정값은 `CFG`/`SHEET` 객체 한 곳에만 둔다 (오픈소스 공개 대비: 설정만 바꾸면 다른 회사도 쓸 수 있게).
- **비밀값 분리**: 웹훅 URL·텔레그램 토큰·chat_id는 코드에 쓰지 않는다. `PropertiesService.getScriptProperties()`의 `CHAT_WEBHOOK_URL`(기본), `TELEGRAM_TOKEN`·`TELEGRAM_CHAT_ID`(폴백)에서 읽고, 속성이 없으면 기준정보 [설정] 탭 `WEBHOOK_URL` 값을 폴백으로 읽는다(리허설 편의 — 더미데이터 설정 탭에 넣어둠). CFG.NOTIFY에는 채널 이름과 속성 키 이름만 둔다. 저장소가 나중에 public으로 바뀌기 때문이다. **심사위원 공유(폴더 뷰어 공개)·public 전환 전에는 [설정]의 WEBHOOK_URL 값을 지우고 스크립트 속성으로만 둔다** — 뷰어에게 노출되면 누구나 그 채팅방에 발송할 수 있다. 스프레드시트·폴더 ID는 CFG에 두되 public 전환 전에 플레이스홀더로 바꾼다.
- 주석은 모든 부서가 이해할 수 있게 상세히 쓴다.
- 단계별로 단독 실행 가능한 테스트 함수를 만든다 (예: testLoadOnly, testAssignOnly, testPublishOnly).

## 작업일지 규칙

- **작업 하나를 끝낼 때마다** `작업일지.txt`에 한 줄 남긴다(단계 완료뿐 아니라 코드 수정·검증·규칙 변경 등 전부 — 사용자 지시 2026-09-03). 형식: 날짜, 완료 한 줄, 다음작업 한 줄. 길게 쓰지 말 것.
- **커밋 단위**: #N 단계 완료 시점과 E2E 성공 시점마다 `/github`(또는 github 에이전트)로 커밋한다. 커밋 메시지 첫 줄은 "#N 단계명: 한 줄 요약". 커밋 전 익명화 검사가 통과해야 한다. 미완료 상태로 커밋하지 않는다.

## 전문가 에이전트 규칙

- `.claude/agents/`에 있는 에이전트만 사용한다. 새 에이전트를 만들거나 덮어쓰지 않는다.
- 목록: production-expert(계획·납기), manufacturing-expert(현장 실행성·교체), coding-expert(GAS 품질·6분 제한), data-analyst(결과 검증), gdrive(clasp 배포 전담 — 코드 수정 금지), github(커밋·푸시 전담 — 코드 수정 금지)
- 스킬: `/anon-check`(익명화 전수 검사), `/github`(커밋·푸시). 검토 에이전트 3개는 읽기 전용이며 코드를 고치지 않는다 — 수정은 coding-expert 또는 메인 세션이 한다.
- 로직 변경·결과 검토 시 필요한 에이전트를 **동시에 병렬 호출**한다. 순차 호출 금지, 역할 통합 호출 금지.
- 사용자에게 계획 결과를 보고하기 전에 전문가 검토를 먼저 거친다.
