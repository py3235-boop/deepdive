## 슬라이드 2 — 문제: 진짜 병목은 전사(轉寫)가 아니었다

**화면**: 왼쪽에 As-Is 흐름, 오른쪽에 "막히는 지점" 한 문장

```
고객사 발주(메일·PDF·사진)  →  담당자가 엑셀로 옮겨 적기  →  월 단위로 생산계획 수립
                                                              ↑
                                        그 사이 들어온 발주는 다음 계획까지 대기
```

**멘트**
> "처음에는 옮겨 적는 일이 문제라고 봤습니다. 그런데 현장에서 실제로 곤란한 순간은 달랐습니다.
> 고객사가 '이 물량 언제까지 됩니까' 하고 물을 때 바로 답을 못 하는 것입니다.
> 답하려면 지금 설비가 어디까지 차 있는지, 규격을 바꾸면 교체 시간이 얼마나 드는지, 휴무가 몇 번 끼는지를 다시 따져야 합니다.
> **발주 정보와 생산 여력이 서로 다른 장부에 있어서, 둘이 만나는 지점이 사람 머릿속에만 있었습니다.**
> 담당자가 자리에 없으면 판단 자체가 멈춥니다."

## 슬라이드 3 — 해결 구조

**화면**: 아키텍처 한 장 (텍스트 그대로 도형화)

```
 ① 발주 문서 판독            ② 출고계획 → 출하계획          ③ 생산계획 자동 수립         ④ 알림
 ─────────────────           ──────────────────────         ────────────────────        ──────
 메일·PDF·이미지             가로 날짜표를                   호기 배정 + 시간 시뮬레이션   Google Chat
 → 품목·수량·납기 추출        세로 4열로 변환                 (설비 여력·교체·휴무 반영)    카드 발송
 → 사람이 검수·확정           (품목·고객사·출하일·수량)
        │                           │                              │                        │
        └─────────── 파일명 패턴으로 자동 감지 · 1분 트리거 ─────────┴────────────────────────┘

 입력: 기준정보 1개(설비·CAPA·휴무·재고) + 출고계획 + 실적 2개
 출력: 생산계획 1개(18탭, 고정 링크) + 호기별 작업지시서 10개 파일
```

**멘트**
> "왼쪽이 발주를 읽는 부분, 오른쪽이 계획을 세우고 알리는 부분입니다. 두 파트가 **출하계획 스프레드시트 4열**로 만납니다.
> 이 인터페이스만 지키면 어느 쪽을 바꿔도 다른 쪽이 멀쩡합니다."

## 슬라이드 4 — 우리가 만든 것

**화면**: 3개 블록

| 만든 것 | 핵심 |
| --- | --- |
| 출고계획 변환 | 폴더 위치와 무관하게 **파일명으로** 찾아 읽는다. 같은 파일을 두 번 처리해도 결과가 같다 |
| 생산계획 엔진 | 설비 10대 · 품목 8종에 대해 어느 호기에서 언제부터 언제까지 만들지 배정 |
| 결과와 알림 | 결과 파일은 **링크가 고정**이고 탭 내용만 바뀐다. 호기별 작업지시서는 파일이 따로 나간다 |

**멘트**
> "설정만 바꾸면 다른 회사도 쓸 수 있게 만들었습니다. 품목 코드, 설비 목록, 거래처 양식, 알림 채널이 모두 설정값입니다. 코드는 손대지 않습니다."

## 슬라이드 5 — 계획 엔진이 지키는 규칙

**화면**: 규칙 4개만 크게

1. **절대 안 되는 조합은 절대 배정하지 않는다** — 품목과 호기 조합 금지 목록, 가닥수 37 이상은 payoff 2대뿐인 호기에서만
2. **규격교체는 피하되, 납기가 걸리면 납기가 이긴다** — 교체는 한 번에 1.5시간이고 되돌릴 때 또 든다. 그래서 기본은 회피지만, 교체 없이 납기를 못 맞추면 교체를 감수한다
3. **주말과 휴무에는 시간이 흐르지 않는다** — 근무일 안에서만 시간을 더한다. 추석 연휴 3일을 걸친 작업은 그만큼 뒤로 밀린다
4. **실적이 있는 구간은 계획하지 않는다** — 어제까지 만든 것은 실적으로 대체하고, 오늘부터만 다시 계획한다. 못 나간 출하는 다음 근무일로 이월한다

**멘트**
> "규칙 두 번째가 이 시스템의 성격을 보여줍니다. 저희 데이터로 돌렸을 때 교체를 한 번 감수하는 대가로 납기 지연 3건과 재고 마이너스 4건이 사라졌습니다.
> 사람이 하던 판단이 바로 이런 교환이었습니다."

## 슬라이드 7 — Before / After

| 구분 | As-Is | To-Be |
| --- | --- | --- |
| 발주가 계획에 반영되는 시점 | 담당자가 옮겨 적고 다음 계획 수립까지 대기 | 파일이 올라오면 **1분 안에** 재계획 |
| "언제까지 됩니까" 응답 | 계획 담당자가 설비 여력·교체·휴무를 다시 계산 | 알림에 **납기 가능 여부와 완료 예정일**이 함께 온다 |
| 계획 주기 | 월 단위 | 발주가 들어올 때마다 |
| 현장 전달 | 담당자가 정리해 전달 | 호기별 파일 10개가 자동 갱신 |
| 담당자 부재 시 | 판단 정지 | 트리거가 대신 돌린다 |
| 입력 오류 | 생산 후 발견 | 검수 화면과 교차검증에서 발견 |

**이번 실행 결과 (더미데이터)**

| 항목 | 값 |
| --- | --- |
| 출고계획 1장 → 출하계획 | 122행 · 99,218kg |
| 실적 반영 | 생산실적 38행 · 출하실적 42행을 집계해 계획 시작 재고 산출 |
| 수립된 계획 | 수요 72건 → 작업 115건(실적 29 + 계획 86) · 83,828kg |
| 규격교체 | 1회 |
| 납기 미달 | 1건 (물리적 불가 — 가용 48시간 대 필요 73.8시간) |
| 재고 마이너스 | 0건 |
| 실행 시간 | 45초 |

**멘트**
> "숫자 하나만 짚겠습니다. 납기 미달 1건은 숨기지 않았습니다. 그 물량은 가용 시간이 48시간인데 73.8시간이 필요해서 어떤 호기에 넣어도 안 됩니다.
> **못 되는 것을 못 된다고 먼저 알려주는 것**이 이 시스템의 값어치라고 생각합니다."

## 슬라이드 8 — 확장과 공개

**화면**: 한 줄씩 3개

- 작업목록 한 장에서 호기별 QR · 태블릿 · 아침 브리핑까지 확장된다
- 처리 결과가 0건이면 완료로 넘기지 않고 경고를 보낸다 — "완료됐는데 실제로는 비어 있는" 상황을 막는다
- 결과물은 오픈소스로 공개한다. 같은 방식으로 발주를 받고 계획을 세우는 지역 중소 제조기업이 그대로 가져다 쓸 수 있다

**멘트**
> "저희 회사만 편해지는 것으로 끝내지 않겠습니다. 설정 파일만 바꾸면 되는 형태로 공개합니다."

## 질의응답 예상 문답

| 질문 | 답변 |
| --- | --- |
| 실데이터가 아니라 더미데이터인가 | 맞습니다. 안내문 권장에 따라 더미데이터로 만들었습니다. 양식은 실제 시스템 내보내기와 열 구성까지 같아서, 실데이터를 그대로 붙일 수 있습니다 |
| 발주 판독 정확도는 어떻게 담보하나 | 인식 결과를 그대로 믿지 않습니다. 총중량 = 단위중량 × 수량처럼 도메인 관계식으로 교차검증하고, 원본과 나란히 놓고 사람이 확정하는 화면을 반드시 둡니다 |
| 두 파트는 어떻게 연결되나 | 출하계획 스프레드시트 4열이 인터페이스입니다. 판독 쪽이 행을 붙이면 이쪽이 변경을 감지해 다시 계획합니다 |
| 규격교체를 줄이는 게 목표인가, 납기가 목표인가 | 기본은 교체 회피입니다. 교체는 손실이 두 배로 들기 때문입니다. 다만 교체 없이 납기를 못 맞추면 납기를 우선합니다 |
| Apps Script의 6분 제한은 문제 없나 | 현재 45초입니다. 시트 입출력을 모두 배치로 처리하고, 탭 하나에 쓰기 한 번을 원칙으로 했습니다 |
| 왜 스프레드시트인가 | 현장이 이미 쓰는 도구입니다. 새 프로그램을 설치하거나 교육할 필요가 없고, 링크만 주면 됩니다 |
| 검증은 어떻게 했나 | 계획 결과에 대해 절대차단·payoff·동시가동·휴무·보빈 배수·시간 겹침·소요시간을 매 실행마다 자동 검사하고, 어긋나면 결과를 쓰지 않고 오류로 남깁니다. 별도로 생산관리·현장·데이터·코드 관점 교차검증도 돌렸습니다 |
